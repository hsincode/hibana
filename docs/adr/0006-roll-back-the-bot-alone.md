# ADR-0006: 切り戻しは bot だけで完結させ、API と DB は 1 つ前の版と互換に保つ

- 状態: 採用
- 決定日・判断者: 2026-10-04、持ち主
- 判断の過程を残した Issue: #3（作り直す範囲）、#5（方式の選択。表の 3・12 と、見直しのコメント）
- 置き換える／置き換えられた ADR: なし

## 要求と決定
- プロダクトの特性と、満たす要求:
  - 配信先が API・Web・bot の 3 つあり、API を最初に出す。bot の配信が失敗すると、relay が bot だけを前の版に戻す。そのとき API と Web は新しい版のまま残る（#1 の観察 4）
  - API は起動時に DB のスキーマを変更する（#1 の観察 10）。配信の切り替え前の確認（ADR-0005）でも、この変更は本番の DB に対して実行される
  - 要求は、版がずれた状態でも全体が動き続けることと、切り戻しのときに DB を触らずに済むこと
- 採用する構成・方式:
  - bot が前の版に戻っても、API・Web は戻さない
  - 規則 1: API は、1 つ前の版の bot・Web からの呼び出しを受け付け続ける。ルート、PATCH が受け付ける設定項目、bot が読むスナップショットの項目を削るときは、2 回の配信に分ける。1 回目で bot・Web がそれを使わなくなり、2 回目で API から削る
  - 規則 2: 起動時の移行は追加だけにする。`CREATE TABLE IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS`、`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` だけを書く。足す列は NULL を許すか、既定値を持たせる。列や表の削除・名前の変更・型の変更は 2 回の配信に分け、1 回目でコードがそれを使わなくなってから、2 回目で手作業の手順として実行する
  - 規則 1 は `apps/api/src/contract.json`（契約の一覧）と `contract.test.ts` で守る。一覧にある項目がコードから消えると検査が落ちる。削るには一覧からも消す必要があり、その差分が PR に出る
  - 規則 2 は `apps/api/src/migrate-rules.test.ts` で守る。移行の SQL に、追加以外の文や、既定値のない `NOT NULL` の列があると検査が落ちる
- 比較した代替案と、採用しなかった理由:
  - API・Web も戻す + up/down つきの移行: 版がそろい、スキーマもコードの版に合わせられる。3 か所と DB を連動して戻す経路は失敗する箇所が最も多く、めったに動かないので壊れていても気付きにくい。down ではデータが戻らないので、破壊的な変更を分ける規則は結局要る。CI から DB に接続するための秘密情報も要る
  - 戻さず、通知だけする: 作る量が最小。互換性を守る仕組みがないまま、ずれた状態で動き続ける
  - up だけを配信の手順に明示する: 変更が手順として見える。DB の接続情報を GitHub に置く必要がある
  - 持ち主は最初に「API・Web も戻す」と「up/down つきの移行」を選び、同じ日に見直して現在の方式に変えた（#5 のコメント）。持ち主の言葉での理由は #5 に追記する

## 影響
- 得られる効果: 切り戻しは bot だけで完結し、DB を触らない。API の配信を取りやめても、すでに実行された移行が前の版を壊さない
- 費用・運用の負荷・残る制約:
  - 設定項目や列を削る変更は、2 回の配信に分ける手間がかかる
  - 検査が見るのは、項目の有無と SQL の種類まで。項目の意味を変える変更（同じ名前で値の解釈を変える、など）は検査では拾えない。そういう変更は新しい名前で足す
  - Web が新しく、API が古い、という逆向きのずれは対象にしていない。配信の順番（API が先）で起きないようにしている
  - スキーマの変更は、配信の手順としては見えないまま（起動時に実行される）
  - 契約の一覧は、項目を足すたびに更新が要る（`bun apps/api/src/contract.ts --write`）
- セキュリティ・障害時の挙動: 規則を破る変更は PR の検査で止まり、main に入らない（ADR-0003）

## 見直す条件
- 2 回に分ける手間が、変更の速さを目立って落とすとき
- 検査を通った変更で、版のずれによる障害が起きたとき（契約に入れる範囲を広げるか、応答の形まで検査する）
