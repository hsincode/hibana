# ADR-0007: sandbox イメージは CI でビルドし、中身と 1 対 1 のタグで配信する

- 状態: 採用
- 決定日・判断者: 2026-10-04、持ち主
- 判断の過程を残した Issue: #3（作り直す範囲）、#5（方式の選択。表の 6・11）
- 置き換える／置き換えられた ADR: なし

## 要求と決定
- プロダクトの特性と、満たす要求:
  - bot は利用者の依頼を、制限をかけた Docker コンテナ（sandbox）の中で実行する。使えるツールはイメージで決まる
  - これまでは VPS の上で `make sandbox-image` を手で実行し、`hibana-sandbox:latest` として使っていた。`apps/bot/sandbox/` を変えても本番のイメージは古いままで、どの commit の定義からできたイメージかも分からなかった（#1 の観察 8）
  - 本番と同じ環境を別に作りにくいので（#3）、本番で動くイメージそのものを CI で作って確かめたい
- 採用する構成・方式:
  - `apps/bot/sandbox/` が変わると、GitHub Actions（`.github/workflows/sandbox-image.yml`）がイメージをビルドし、同梱したツールが起動することを確かめる。PR ではここまで
  - main では、確かめたイメージを `ghcr.io/hsincode/hibana-sandbox` に配信する
  - タグは `apps/bot/sandbox/` の git tree hash にする。ディレクトリの中身が同じなら同じタグ、違えば違うタグになる。同じタグがすでにあれば、ビルドも上書きもしない
  - Blender をイメージから外し、Blender に依存する `outline-edits` スキルを削除する
- 比較した代替案と、採用しなかった理由:
  - relay が VPS の上でビルドして commit のタグを付ける: レジストリが要らない。本番のホストにビルドの負荷がかかる。ベースイメージやパッケージが動くので、同じ commit でも中身が変わりうる
  - CI ではビルドの検査だけをして、本番への反映は手作業のまま: 作る量が最小。commit とイメージの対応は記録頼みのまま
  - `outline-edits` を別のイメージに分ける／残して無効にする: スキルが残る。イメージが 2 種類になって切り替えの仕組みが要る、または動かないコードが残る
  - 持ち主の言葉での理由は #5 に追記する

## 影響
- 得られる効果:
  - イメージがどの中身からできたかが、タグで決まる。PR の段階で、イメージがビルドできて起動することを確かめられる
  - Blender を外した分、イメージが小さくなる（外す前は手元のビルドで 5.27 GB。外した後の大きさは「実装と検証」に書く）
- 費用・運用の負荷・残る制約:
  - **この ADR の時点では、本番の bot はまだ配信したイメージを使っていない。** bot が参照するのは `SANDBOX_IMAGE`（既定は `hibana-sandbox:latest`）で、VPS のローカルのイメージのまま。配信したイメージを digest で参照させるのは、bot の配信物を固定する変更（#5 の 5・9・10）で行う
  - `hibana-video`・`hibana-vpn`・音声合成のイメージは対象にしていない。手元でのビルドのまま
  - `outline-edits` スキルは使えなくなる。戻すには Git の履歴から復元し、Blender を入れ直す
  - タグは tree hash なので、README だけを変えても新しいタグでビルドし直す
  - イメージの中で取得するもの（apt、pip、npm のパッケージ）は、版を固定していないものがある。同じ tree hash でも、ビルドした日によって中身が変わりうる。一度配信したタグは上書きしないので、配信済みのイメージは変わらない
- セキュリティ・障害時の挙動:
  - 配信に使うのは、その実行だけに発行される `GITHUB_TOKEN`（`packages: write`）。PR の実行では配信しない
  - ビルドか起動の確認が失敗すれば、配信しない

## 見直す条件
- video・vpn のイメージでも、定義と本番のずれで問題が起きたとき（同じ仕組みに載せる）
- ビルドの時間が長く、PR の待ち時間が問題になったとき（レイヤーのキャッシュを使う）
