# ADR-0008: 会話履歴と Auto Routing の経路を SQLite に保存し、再起動をまたいで保つ

- 状態: 採用
- 決定日・判断者: 2026-10-10、持ち主
- 判断の過程を残した Issue: #59（保存の方式・範囲・保持期間の比較と、本人の判断）
- 置き換える／置き換えられた ADR: なし

## 要求と決定
- プロダクトの特性と、満たす要求:
  - bot は、`main` への push で relay が `systemctl restart hibana` を実行して入れ替わる（ADR-0001）。本番の再起動は、2026-10-07〜10-10 の 4 日間で 16 回あり、すべてデプロイによるものだった（#59）
  - 会話履歴（`History`）と Auto Routing の経路（`RouteMemory`）は、プロセスのメモリにしか無かった。再起動のたびに、全チャンネルで会話が最初からになり、経路も選び直しになっていた
  - 要求は 2 つ。デプロイ・クラッシュ・VPS の再起動をまたいで会話が続くこと。再起動後の最初のリクエストが、再起動前の最後のリクエストへの追記だけになること（Anthropic のプロンプトキャッシュは Anthropic 側に 1 時間残るので、先頭とモデルが同じなら再起動後も当たる。#31）
- 採用する構成・方式:
  - `HIBANA_DATA_DIR/conversations.db` に、Bun 同梱の SQLite（`bun:sqlite`）で保存する。場所は `CONVERSATION_DB_PATH` で変えられ、空文字にすると保存しない（メモリだけで動く）
  - 表は 3 つ。`history_channels`（チャンネルごとの guild・モデルのキー・直近の usage）、`history_turns`（ターンごとのメッセージ。`seq` がチャンネル内の順番）、`routes`（チャンネルごとの経路と最後に使った時刻）
  - `History` と `RouteMemory` は、これまでどおりメモリを作業用の写しとして持つ。変更のたびに同じ内容を書き込み（ターンの追加は 1 行の追加）、チャンネルは起動後に最初に使うときに読む。保存の実装は `apps/bot/src/conversation-store.ts`
  - 保存する範囲は、会話履歴と Auto Routing の経路だけ（#59 の 2-b）。ワークフローの完了済み結果、先頭一致の比較相手、フォールバックを知らせたかどうかは、これまでどおりメモリだけ
  - 保持期間は、メモリ上の規則と同じ（#59 の 3-ア）。スレッドは無操作が設定の時間（既定 1 時間）を超えると次の発言で破棄し、通常のチャンネルは期限なしで、トークンの上限でだけ古いターンを落とす。`/clear`・チャンネルやスレッドの削除・モデルの変更・guild の設定変更は、保存した分も消す
  - 規則: スキーマの変更は追加だけにする（`CREATE TABLE IF NOT EXISTS`・`CREATE INDEX IF NOT EXISTS`、列を足すなら NULL を許すか既定値を持たせる）。配信に失敗すると relay が bot を前の commit に戻し（ADR-0006）、前の版が、新しい版の残したファイルを開くため。`conversation-store.test.ts` の「schema」で守る
  - 起動時に保存済みの設定を読むこと（`runtime.load()`）と、bot が初めて受け取るスナップショットは、設定の「変更」として扱わない。変更として扱うと、guild の履歴を消す処理が起動のたびに全 guild で走り、保存した履歴が残らない。bot が止まっている間にダッシュボードで変えた設定は、起動時の同期で、保存済みの設定との差として検出する
- 比較した代替案と、採用しなかった理由（#59 の比較表）:
  - チャンネルごとの JSON ファイル: 既存の保存（`atomicJson`）と同じ作りで、新しい技術が入らない。ターンごとにチャンネルのファイル全体を書き直す。AI はこの案を勧めたが、持ち主は SQLite を選んだ。持ち主の言葉での理由は聞いていない
  - API 側の DB（Neon）: VPS を作り直しても残る。会話の本文がクラウドの DB へ出る。ターンごとに Vercel の関数を呼ぶので、使用量の超過（#27）が再発しうる
  - Discord のメッセージから作り直す: 保存するデータが増えない。ツールの呼び出しと結果が戻らず、送る内容が再起動の前と変わるので、キャッシュが続かない
  - 何もしない: デプロイのたびに会話が消え続ける

## 影響
- 得られる効果:
  - デプロイをまたいで会話が続く。再起動後の最初のリクエストは、再起動前の最後のリクエストと先頭が一致する
  - Auto Routing のチャンネルは、再起動後も同じモデルと effort を使う。Jev の選び直しと「Auto Routing:」の再表示が無くなる
  - 再起動でチェックポイントから再開したターンは、終わった後、それより前の履歴に続けて保存される（以前は、そのターンだけが残った）
- 費用・運用の負荷・残る制約:
  - 会話の本文（ツールの結果を含む）が、VPS のディスクに残る。通常のチャンネルは期限が無い。以前は、再起動が事実上の消去になっていた。チェックポイントと日次ログには、以前から本文や操作の記録が残っている
  - ファイルは、使われたチャンネルの数だけ大きくなる。1 チャンネルの上限は `HISTORY_MAX_TOKENS`（既定 16 万トークン）。使われなくなったチャンネルや、アーカイブされたスレッドの行は、消す操作があるまで残る。大きさは実測していない
  - bot が止まっている間に削除されたチャンネルの行は、消えない（削除のイベントを受け取れないため）
  - 保存したメッセージの形（`Message`）も、スキーマと同じ扱いになる。項目の意味や名前を変えると、保存済みの会話を新しい版が読み違える。変えるときは、新しい名前で足す
  - 切り戻しの間、前の版はこのファイルを使わない。その間の会話は保存されず、新しい版に戻ると、切り戻す前の履歴の続きになる
  - bot は 1 プロセスで動かす前提。同じファイルを 2 つの bot が使う構成は想定していない
  - バックアップは取っていない
- セキュリティ・障害時の挙動:
  - ファイルのモードは 0600（`-wal`・`-shm` も同じ）。秘密情報は入れない。会話の本文は入る
  - ファイルを開けない、または書き込みに失敗したときは、エラーを記録して、メモリだけで動き続ける。ターンは失敗にしない。開けなかったファイルは、調べられるようにそのまま残す
  - 読めない行があるチャンネルは、そのチャンネルだけを空にして始め直す（壊れた会話の一部だけを送らない）
  - WAL と `synchronous = NORMAL` を使う。プロセスが強制終了しても、書き込み済みのターンは残る。電源が落ちた場合は、直近のターンを失うことがあるが、ファイルは壊れない
  - 保存した会話は、書いたときの guild（または DM）でだけ続ける。行の guild が呼び出しと違えば、空から始める
  - 保存した経路は、いまの routing の段（`AUTO_ROUTE_LEVELS`）にあるものだけを使う。デプロイで段が変わったら、選び直す
    - 2026-10-10 追記（#35）: 難易度の段から Sonnet が外れた。Sonnet の medium / high は、依頼でモデルを指定したときにだけ届く経路（`AUTO_ROUTE_REQUEST_ONLY`）として残したので、保存済みの Sonnet の経路はそのまま使う

## 実装と検証
- 適用した commit・構成図: この ADR を追加した PR
- 要求ごとの検証記録（`apps/bot/src/__tests__/conversation-store.test.ts`、手元で実行）:
  - 再起動をまたぐ会話: ターンごとに保存先を開き直しても、2 回目以降のリクエストがすべて「直前のリクエストへの追記」になり、送る内容が、開き直さない場合とバイト単位で一致する
  - 強制終了: 子プロセスが 2 ターンを書いた後に SIGKILL で終了しても、次のプロセスが 2 ターンとも読める
  - 消える条件: `/clear`、guild の設定変更（まだ読んでいないチャンネルを含む）、モデルの変更、スレッドの期限切れ、別の guild からの読み出し
  - 起動: 保存済みの設定の読み込みでは履歴が消えず、その後の設定変更では消える（`sync.test.ts` に、初回のスナップショットと、停止中の変更の検出）
  - 異常系: 読めない行、SQLite ではないファイル、書き込みの失敗、空のパス、ファイルのモード
  - 切り戻し: 新しい版が列や表を足したファイルを、この版が読み書きできる
  - bot 全体: 同じデータディレクトリで bot を作り直すと、次のターンが前のターンを含み、Jev を呼ばずに同じ経路を使う
- 実際の運用・CI/CD の実行記録: 未配信。配信後に、PR と #59 に追記する
- 検証していない範囲: 本番での動作、実際の会話でのファイルの大きさと書き込みの時間、実 API でのキャッシュのヒット率の変化、電源断

## 見直す条件
- ファイルの大きさがディスクの空きを圧迫するとき（保持期間を決め直す。#59 の 3）
- 保存の失敗が繰り返しログに出るとき
- bot を複数のプロセスで動かすとき
- チェックポイントやワークフローの結果も、同じ場所に移すと決めたとき
