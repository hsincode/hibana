# ADR-0011: プロバイダー「Anthropic Workspace」を足し、Claude Managed Agents のセッションで動かす

- 状態: 採用（2026-10-12、持ち主が PR #77 のマージを指示した。マージ先は #73 のブランチ `feat/claude-harness` で、main に入るのは #73 がマージされたとき。実 API では、Haiku 5.5 のセッションだけを同じ日に確認した: Ultra なしの全項目と、Haiku Ultra の bot 自身のターン 1 回。#76 の未決の点は、AI の案のまま実装してあり、本人未確認）
- 決定日・判断者: 次の 4 項目は 2026-10-12、持ち主（#76 の原文）。プロバイダー「Anthropic Workspace」として足すこと。既存のサンドボックスではなく、クラウドの作業領域を前提にすること。既存のツールは入れられるものを入れ、入れられないものは無理に入れないこと。モデルは、Haiku Ultra に対応するほかは同じにすること。それ以外（下で「AI の案」と書いた点。上限の値を含む）は AI の案のまま実装しており、本人未確認
- 判断の過程を残した Issue: #76（本人の原文、AI の解釈、まだ決まっていない 11 点の比較）、#66（Managed Agents を不採用にした比較）、#67（非推奨の線引き）、#68（Anthropic の委譲）、#35（Auto Routing）、#44（利用額）
- 置き換える／置き換えられた ADR: なし。ADR-0009 が代替案として不採用にした「Managed Agents」を、`anthropic` のターンの置き換えではなく、別のプロバイダーとして足す。ADR-0009（`anthropic` は `claude` ハーネス）と ADR-0010（非推奨の 14 種と凍結）の対象は変えない。ADR-0008 の保存先（`conversations.db`）に、表を 2 つ足す

## 要求と決定
- プロダクトの特性と、満たす要求:
  - 作業領域は bot の機械の Docker サンドボックスで、サーバーの通常のチャンネルは 1 つを共有している。Anthropic のターンの委譲は `Agent` ツールだけで、Ultra は無い（#68）
  - 持ち主の要求（#76 の原文）: 作業領域もクラウドにあり、Haiku Ultra にも対応したものを、プロバイダー「Anthropic Workspace」として足す。直前のやりとりでの発言は「Haiku Ultra などとして公式 API の機能を使った実装にしたい」
  - AI の解釈（本人未確認）: 「公式 API の機能」は Claude Managed Agents の dynamic workflows。「クラウドの作業領域」は Managed Agents の cloud environment のコンテナ。「Haiku Ultra」は、Haiku 5.5 のときだけ dynamic workflows を有効にすること。「モデルは同じ」は、`anthropic` と同じ 3 モデル（Haiku 5.5 / Sonnet 5.5 / Opus 5.5）で、Auto は含めない
  - 併せて守る要求: 既存の 2 つのハーネスが送るリクエストを変えないこと（#67）。guild / DM の分離と権限チェックを保つこと。費用に上限を置くこと（AGENTS.md）。bot だけで切り戻せること（ADR-0006）
- 採用する構成・方式（プロバイダーとして足すこと以外は AI の案。本人未確認）:
  - provider `anthropic_workspace`（表示名は Anthropic Workspace）。プリセットは 3 件（Premium 以上が設定でき、サーバーで共有できる。`anthropic` と同じ）。最初は非公開で入れ、持ち主が `/models` で公開する。設定 API を使わない bot（`WEB_API_URL` なし）には公開の手段が無いので、そこでは常に非公開・Premium 以上として扱い、使えるのは `PROVIDER=anthropic_workspace` を既定にしたときだけにする。Auto のプリセットは作らず、Auto Routing は `anthropic` だけのままにする（#35）。非推奨でないプロバイダーは `anthropic` と `anthropic_workspace` の 2 つになる
  - 認証情報は `ANTHROPIC_WORKSPACE_API_KEY` だけ。`ANTHROPIC_API_KEY` へのフォールバックはしない（プロバイダーごとに独立した認証情報）
  - 3 つ目の実行経路 `workspace`。ターンは Managed Agents のセッションへの 1 回の発言で、ループ・会話・作業領域は Anthropic 側にある。内容は [docs/harness.md](../harness.md) の「workspace 経路」
  - 公式 SDK `@anthropic-ai/sdk` を **0.133.0 に固定**して、この経路だけで使う。dynamic workflows と budget の型が入った版で、beta の型は版ごとに変わりうるので、範囲指定にしない。`codex` と `claude` の送受信は、従来の `fetch` の実装のまま変えない（ADR-0009 で SDK への置き換えを見送った判断は、その 2 つについてはそのまま）
  - エージェントは 2 つ（委譲なしの plain と、dynamic workflows だけを有効にした ultra）、environment は 1 つ。最初のターンで作り、ID を `HIBANA_DATA_DIR` に保存する。モデル・effort・システムプロンプト・ツールは、セッションの作成時に上書きして渡す
  - セッションはチャンネルごとに 1 つ（スレッド・DM を含む）。対応は `conversations.db` の新しい表 `workspace_sessions`、片付け待ちは `workspace_disposals`（追加だけ。後から足した列 `lease_settled`・`allowed_cents` は、列の無いファイルを開いたときに `ALTER TABLE … ADD COLUMN` で足す）。`/clear` とチャンネルの削除はセッションを delete し、モデルや設定の変更・スレッドの期限切れは archive する
  - ツールは、Managed Agents の組み込みの 8 個と、Hibana の Discord・設定・サイト・Jev のツール最大 76 個（custom tool）。入れないのは、bot のサンドボックスのファイルやイメージに依るもの（スキル、サイトの公開、画像生成、`Agent`、ブラウザーとメディアのダウンロード、VPN、GitHub ログイン、Exa）。一覧は話す人によらず同じにし、可否は呼び出しのたびに、そのターンの依頼者の権限で `ToolRegistry.execute` を通して判定する。ファイルを渡すのは `send_file` だけで、コンテナの `/mnt/session/outputs/` から Files API で取る
  - Haiku Ultra は、既存の Ultra のスイッチが on で、モデルが Workspace の Haiku 5.5 のときだけ働く。xhigh に固定しない。キーワード `ultracode` は効かない。workflow run を始めるのはエージェントで、プロンプトには「分けられる大きな仕事のときだけ」「同時に 1 つまで」と条件つきで書く。run の中からの Hibana のツールは読み取りだけにし、run を始めた人の権限で判定する
  - 上限は、1 ターンの金額（Anthropic 側の session budget。$1、Haiku Ultra は $3）、1 日と月の金額（bot の台帳。$5 と $50）、1 ターンの時間（20 分、Haiku Ultra は 60 分）、bot 全体の同時ターン数（2）、入力長（60,000 字）。値は環境変数で変える。**回数の上限は置かず、金額・時間・同時数で代える**（ループが Anthropic 側にあり、bot は往復を数えて止められないため。#76 の 3）
  - 1 ターンの金額の上限は 0.05 USD 未満にできない（枠が 5 セント未満のターンは始めないため。範囲外は起動時のエラー）。1 日と月の判定には、報告された額に、セッションを 1 つ作るたびの 1 セントと、使用量（トークン、稼働秒数など）が増えたのに額が報告されなかった区間の枠の全額を足した額を使う（報告は 1 セント単位の四捨五入で、短いセッションの繰り返しが上限に届かないため。`/usage` の表示は報告された額のまま）。使用量の報告がまったく無かった区間は、何も使っていないものとして扱い、枠を足さない（発言が取り上げられる前に、`/clear`・言い直し・時間切れで終わったターン。受理されただけで枠の全額を数えると、数回でその日の全員のターンを断ることになるため）。再開（`/retry`、起動時）も、同じ台帳と上限で確かめる
  - 枠を足すのは「使用量の報告があるのに、額の報告が無い」区間だけで、1 つの枠につき 1 回。その使用量を最初に読んだ処理（ターンの精算、ターンの後の掃除、会話が終わった後の片付け）が足す。足し終えたことは lease の印（`counted`）で覚え、budget を下げられずに lease が残っても数え直さず、1 日と月の枠の予約にも重ねない。使用量も額も見えないまま終わったターンは、budget を下げた後も lease を印（`lowered`）つきで残し、次の掃除（60 秒ごと）か、その前の片付けが読んで、使用量（額なし）が出ていれば足す（この lease は予約に入れない。代案は「予約に入れる」で、上限の近くで、言い直しの 2 つ目のターンが断られる）。片付けに回るセッションには、その時点でまだ数えていなかった枠を持たせる
  - 使用済みなのに額を報告しないセッションでは、ターンを始めない（上限を「使った額 + 枠」で置けないため）。使用済みと見なすのは、使用量の報告がある、bot が以前に使用量を数えている、処理済みの発言がある、のどれかのとき。取り上げ前の発言がキューにあるだけなら始め、その発言は前の作業として扱う（先に `user.interrupt` を送り、その出力をこのターンの返信にしない。代案は「何もせず、idle のセッションとして扱う」）。調べるのは、額の報告が無いセッションだけ。処理済みの発言があるかは、発言の一覧を、見つかるか尽きるまで読んで決める（1 ページ目で止めない。一覧の並びと 1 ページの件数は実 API で確かめていないため）。10,000 件読んでも、または一覧のリクエストを 20 回送っても決まらなければ、使用済みとして断る（代案は「取り上げ前の発言あり」として始める。20 回は根拠のある値ではない）
  - 同じチャンネルのターンは、発言した人によらず 1 つずつ実行する（bot のチャンネルごとのキュー。既存の 2 つのハーネスと同じ）。1 つのセッションに 2 つのターンを入れない
  - budget で止まったセッションへの次の発言は、budget を上げた後、`user.interrupt` と一緒に 1 リクエストで送り、上げたことで再開した前の作業を止めてから始める。前の作業の続きは、このターンの返信にしない（代案は「このターンの成果として見せる」）
  - 再開の前に、チェックポイントの発言がセッションの最後の発言のままかを確かめる。別の人の発言が間に入っていたら、「続けて」ではなく、本人の発言を新しい発言として送り直す（別の人の依頼を、再開した人の権限で続けないため）
  - チェックポイントは、溜まった発言のうち何件目までをセッションが受け取ったかを覚える。まだ送っていない発言（受理された発言の後で、送る前に失敗したターンのもの）が残っていれば、`/retry` と起動時の再開は「続けて」の代わりにその発言を送り、次の発言はそれを前に付けて送る。どちらも新しい発言として、新しい枠と新しい時間の上限で動く。この形では、セッションの最後の発言の確かめをしない（代案は「常に確かめ、違っていれば全部を送り直す」）
  - まだ送っていない発言と新しい発言を 1 つにまとめると入力長の上限を超えるときは、新しいものから順に、収まるだけを送る。いちばん新しい 1 件は必ず送り、断るのは、その 1 件だけで上限を超えるときだけ。送らなかった件数は返信に 1 行で付け、送らなかった発言は済んだものとして扱う（後から送り直さない）。代案は「合わせた長さで断り、定型文にその旨を書く」「返信ではなく、送る時点で別の発言として知らせる」
  - ストリームを開き直したとき、自分の発言が処理済みとして一覧に無ければ、一覧のイベントを再生しない（前のターンの返信と、答えの付いていない前の呼び出しを、このターンのものにしないため）
  - 届かなかったツールの結果は送り直す（ツールは再実行しない）。400 で断られた結果には、定型の error の結果を 1 回だけ送る
  - 本文なしで終わり、チャンネルに何も届いていないターンは、定型文を返信にする（自動では送り直さない）
  - bot がサーバーから外されても、そのサーバーのセッションは片付けない（既存の 2 つのハーネスが、履歴と作業領域を残すのに合わせる）
  - コンテナのネットワークは、既定で `unrestricted`（環境変数で `limited` と許可するホストの一覧にできる）
  - プロンプトと、書き直したツールの説明は、公開文書をもとに自作する（docs/harness.md の「出所」）
- 比較した代替案と、採用しなかった理由（理由の整理は AI によるもので、持ち主の言葉での理由は聞いていない）:
  - `anthropic` のターンを Managed Agents に置き換える（#76 の案 B）: 経路は増えないが、既存の会話・作業領域・サブエージェントの形が変わり、#66 の決定と #69 の比較の前提が変わる
  - 既存の Workflow（Ultracode）を `anthropic` に出す（#68 の 2b）: 作業領域がクラウドにならない。root が xhigh になり、金額の上限を置けない。文面の出所の問題（#68 の 3）を先に決める必要がある
  - まだ決まっていない点ごとの代替案（専用のプリセット「Haiku Ultra」、ターンごとのセッション、会話だけを消す `/clear`、`limited` のネットワーク、生の HTTP での実装、スキルとサイトの公開を Files API 経由で入れる、など）は #76 の表にある。実装は AI の推奨の側で進めてあり、決まったら直す

## 影響
- 得られる効果:
  - bot の機械の CPU・メモリ・ディスクを使わない作業領域（公開文書の記述では、メモリは最大 8 GB、ディスクは最大 10 GB）
  - Haiku 5.5 での並行作業（workflow run）
  - 1 ターンの金額の上限を Anthropic の側に置けるので、bot が落ちても効く。`anthropic` のサブエージェントには、金額の上限がまだ無い（#68）
  - 既存の経路は変えないので、影響を受けるのは、このプロバイダーを選んだサーバーと利用者だけ
- 費用・運用の負荷・残る制約:
  - 料金は、トークンのほかに、セッションが `running` の間の $0.08 / 時と、web 検索 $10 / 1,000 回（料金ページ、取得日 2026-10-11〜12）。budget は list cost（公開単価）で数え、上限をまたいだリクエストは最後まで実行される。workflow run では、動いているスレッドごとに 1 リクエストぶん超えうる
  - 上限の既定値は、実測にもとづく値ではない。実際の 1 ターンの額は分かっていない
  - サーバーの中で、チャンネルをまたいでファイルを共有できなくなる。コンテナの中身は作成から 30 日で失われ、モデルや設定の変更・`/clear` でも失われる。`/clear` が作業ファイルも消すので、ほかの経路と意味が違う
  - セッションの設定（プロンプト・ツール・web の有無）は作成時に固定される。直して配信しても、既にあるセッションには届かない
  - 使えないもの: スキル、サイトの公開、画像生成、`Agent`、bot のブラウザーとメディアのダウンロード、VPN、GitHub ログイン、Exa、Jev の行動選択モード
  - beta（`managed-agents-2026-04-01`、dynamic workflows）に依存する。run の同時数などの上限は Anthropic のサーバーが決める。SDK を固定しているので、beta の変更への追従は手作業になる
  - 経路が 3 つになる。既存の 2 つは `harness-freeze.test.ts` と `claude-harness.test.ts` で固定したまま
  - archive したセッションと、定義を変える前のエージェント・environment は消さないので、Anthropic 側に溜まる
  - workflow run が開いたままのセッションは、delete / archive が 400（`workflow_run_open`）で拒否されることがある（公開文書の記述。実 API では未確認）。実装は、上限や追加発言で止めた run を開いたまま残し、片付けは 5 回失敗すると次の起動まで試さないので、Haiku Ultra のチャンネルでは、`/clear` やモデルの変更の後も、会話と作業ファイルが Anthropic 側に残りうる。止まった run は、寿命（既定 24 時間）が過ぎるまで自分では終わらない
  - 1 日と月の判定は、多めに数える側に倒している（上の 1 セントと枠の全額。チェックポイントだけが覚えていたセッションは累計の全額）。実際より早く上限に達して、ターンを断ることがある。少なく数える側の穴は 4 つある（どれも、1 ターンの上限は Anthropic 側で効く）。使用量を何も報告しない区間を 0 と数える（作業したのに何も報告しないセッションが実 API にあるかは未確認）。使用量も額も見えずに終わったターンの枠は、次の掃除が 1 回読んだ後で初めて出た使用量には足さない。同じセッションに次のターンが新しい枠を付けると、前のターンのまだ数えていない枠は捨てる。チェックポイントだけが覚えていたセッションは枠を持たない。逆に、予約に入れていない枠が後から足されると、判定用の額が上限を超えることがある（[docs/harness.md](../harness.md) の「限界」）
  - 実 API の挙動しだいで起きる誤りが、ストリームの開き直しに 2 つ、取り上げ前の発言の扱いに 1 つ残っている。開き直した直後に、前の作業の最後のイベントと発言の `processed_at` が同じ時刻だと、前の作業の最後の文を返信にしてターンを終え、budget を下げて本物のターンを止める。`processed_at` が処理の終わりに付く API なら、休んでいたセッションへのターンは、接続が切れていた間のツール呼び出しを取りこぼし、時間の上限まで待つ。額を報告するセッションに取り上げ前の発言が残っていると、前の発言への出力が返信になりうる。どれも偽の応答での再現で、直し方は smoke の結果（時刻の精度、一覧の順序、`processed_at` が付く時点）を見てから決める（[docs/harness.md](../harness.md) の「限界」）
  - Haiku Ultra で run が開いたままターンが終わると、モデルが止まるときに書いた文が、進捗と返信の 2 回出る
- セキュリティ・障害時の挙動:
  - 組み込みのシェル・ファイル・web のツールは Anthropic 側で動き、bot は 1 件ごとの権限チェックを挟めない。利用停止と権限を確かめるのは、ターンの開始時、Hibana のツールが呼ばれたとき、イベントを読むたび
  - コンテナは、既定では外に出られる。読んだ内容に動かされて、コンテナの中身を外へ送る危険は、公開文書が挙げている。秘密情報はコンテナに入れない（bot の鍵やトークンは渡していない）
  - Files API のファイルは、同じ Console workspace のどの鍵からも読める。**Workspace 専用の Console workspace を作り、その鍵を使い、spend limit を設定することを勧める**（#76 の 8。本人の判断待ち）。bot が壊れても効く歯止めは、この spend limit と session budget だけ
  - 鍵・`authToken`・接続先は必ず明示して SDK に渡すので、環境変数 `ANTHROPIC_API_KEY`・`ANTHROPIC_AUTH_TOKEN`・`ANTHROPIC_BASE_URL`（この配備では、ほかのプロバイダーのもの）がこの経路に混ざることはない（`workspace-client.test.ts`）。ただし SDK は環境変数 `ANTHROPIC_CUSTOM_HEADERS` を読んでヘッダーに足すので、bot の環境にこの変数を置くと、Workspace のリクエストにも付く。SDK はこの変数の行を認証のヘッダーの上に重ね、同じ名前を綴り違いで 2 回書くと、クライアントに渡した値では片方しか上書きできない。そこで、SDK に渡す `fetch` の中で、送信の直前に `x-api-key` を Workspace の鍵に設定し、`Authorization` を消している（SDK の重ね順に依らない。ストリームとファイルの取得も同じ `fetch` を通る）。鍵と `Authorization` は置き換わらず、認証以外のヘッダーはそのまま付く（`workspace-client.test.ts`。SDK 0.133.0 のコードの読み取りと、偽の `fetch` でのテストによる。実 API には送っていない）。本番の bot は `fetch` を渡さず、グローバルの `fetch` を包んで使うので、その経路は、`fetch` を渡さずに 127.0.0.1 のサーバーへ送るテスト 1 件で確かめている。クライアントに渡す値も残している（SDK が、認証のヘッダーの無いリクエストを送信前に断るため）。確かめた範囲では、両方のヘッダーを「正規の綴りが先、別の綴りが値なし」で書いた場合に、SDK が送信前にエラーにする（リクエストは出ず、鍵も出ない）
  - 止め方: **プリセットを非公開に戻しても、既に選んでいるサーバーは動き続ける。** 止めるには、鍵を外す（Workspace を選んでいるサーバーの全ターンが認証エラーになる。ほかのモデルには切り替わらない）か、サーバーごとにモデルを替える
  - 切り戻し（bot だけを前の版に戻したとき。ADR-0006）: 新しい表は読まれないだけで残る（前の版 `c657acd` の `conversation-store.ts` と `history.ts` の読み取りと、その 2 つのファイルを、新しい版が書いたファイルに対して手元で動かした確認による。前の版の bot 全体は動かしていない）。**前の版の bot は、Workspace のチェックポイントを `codex` のものとして扱うことがある**（前の版のコードの読み取りによる。未検証）。**切り戻している間の `/clear` やチャンネルの削除は、クラウドのセッションに届かない**ので、新しい版に戻すと、消したはずの会話と作業ファイルが続く
  - 再起動: セッションを止めて budget を下げ、チェックポイントを残す。起動後は、残ったセッションの片付けを最初に始め（Discord のコマンド登録より前）、それが済んでから、1 回だけ自動で再開する。以後は `/retry` を待つ。会話の保存先が無い bot がターンの途中で落ちたときは、チェックポイントだけが覚えているセッションを、再開のときに止めて archive する
  - 利用額の台帳を読めていない間は、新しい発言も再開も断り、残ったセッションの片付けは budget を下げるだけにする（額の記録と delete / archive は、台帳を読めたプロセスが行う）
