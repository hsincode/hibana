# Anthropic Workspace（Managed Agents の経路）

プロバイダー `anthropic_workspace`（表示名は Anthropic Workspace）のターンは、Claude Managed Agents のセッションへの 1 回の発言です（判断記録 #76、[ADR-0011](adr/0011-add-anthropic-workspace-provider.md)）。bot は発言を送り、イベントを読み、Hibana のツールが呼ばれたら実行して結果を返します。モデルを呼ぶループ、会話の保存、シェルとファイルの操作は Anthropic 側で動きます。この文書では、この経路を「workspace 経路」と呼びます。

ほかのプロバイダーのターンは、これまでどおり bot 自身のループ（`Agent.run`）で動きます。どちらで動くかは、ターンのプロバイダーだけで決まります（`apps/bot/src/workspace/select.ts` の `harnessFor`）。

|                    | ほかのプロバイダー                                                                                | `anthropic_workspace`                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| ループを回すもの   | Hibana（`Agent.run`）                                                                             | Anthropic（Managed Agents のセッション）                                                                                    |
| システムプロンプト | `apps/bot/prompts/harness/codex.md` と `apps/bot/prompt.md`                                       | `apps/bot/prompts/harness/workspace.md`。Haiku Ultra のセッションは `workspace-ultra.md` を後ろに足す                       |
| ツール             | シェルとファイルのツールと、`mcp__` 名の統合ツール全件                                            | Managed Agents の組み込みの 8 個（`bash`・`read` など）と、Hibana のツール最大 76 個（custom tool。`mcp__` を付けない名前） |
| 作業領域           | bot の機械の Docker サンドボックス。サーバーの通常のチャンネルは 1 つを共有する                   | Anthropic のクラウドのコンテナ。チャンネル・スレッド・DM ごとに別                                                           |
| 会話の縮め方       | 古いターンを落とす。スレッドは古い側を要約する                                                    | Anthropic 側が持つ。bot は会話を送り直さない                                                                                |
| サブエージェント   | off / on / ultra / multi（`docs/multi-agent.md`、`docs/ultracode.md`）。`anthropic` は off（#35） | Hibana の委譲は無い。Haiku 5.5 で ultra のときだけ、Managed Agents の dynamic workflows（[Haiku Ultra](#haiku-ultra)）      |

ほかのプロバイダーのターンが送るもの（ツール一覧・プロンプト・設定の解決結果）は、Workspace の鍵を設定してプリセットを公開した状態でも、鍵の無いときとバイト単位で同じです（`workspace-settings.test.ts`）。既存のプロンプトとツール定義のファイル（`prompt.md`、`prompts/harness/codex.md`、`tools/definitions.json`、`tools/codex-definitions.json`）は変えていません。

## この文書とコードの由来

この経路は、最初、Claude ハーネスへの作り直し（PR #73。保留中）の上に実装しました（PR #77）。持ち主の判断（2026-10-12、#76）で、この機能だけを `main` に載せ替えています。**下の「実 API での確認」は、載せ替える前のコード（PR #77 の `6f4b8fd`）で行ったものです。載せ替えた後のコードは、実 API に当てていません**（自動テストと、127.0.0.1 の偽のサーバーでの確認だけです）。

載せ替えで変えたこと（AI による。本人未確認）:

- 経路の判定と会話のキーは `apps/bot/src/workspace/select.ts` に置きました。経路は 2 つ（bot 自身のループと、workspace 経路）です。ほかのプロバイダーの会話のキーは、今までと同じ文字列です
- 画像の取り込み（`workspace/images.ts`）、`AskUserQuestion` の定義と結果の整形（`workspace/tools.ts`）は、PR #73 のモジュールから同じ内容を移しました。`AskUserQuestion` の定義は、移す前と同じ文字列です
- `set_bot_model` の説明文のうち、「ほかのプロバイダーは非推奨」に触れていた 4 か所を直しました（`workspace/tools.ts`）。セッションに渡るツール定義は、その分だけ、確かめたものと違います
- `anthropic` のターンは、`main` のとおり、サブエージェントなしのままです（#35）。設定の解決（`Runtime.resolve`）で Workspace のために足したのは、`workspace_ultra` の 1 項目だけです
- ログでターンをまとめる id（`Context.turnId`）は、Workspace のターンにだけ付けます（PR #73 は全ターンに付けていました）。ほかのプロバイダーのターンの文脈・チェックポイントには何も足しません
- テストは、`main` の規則（`anthropic` はサブエージェントなし、非推奨の区別なし）と、`main` の画面テストの fixture に合わせて直しました
- 入れていないもの: Claude ハーネス（#66）、Anthropic 以外のプロバイダーの非推奨化（#67）、Anthropic のサブエージェント（#68）と、それらの文書・ADR-0009・ADR-0010。エラーの分類に `api_error`・`timeout_error` を足す変更も入れていません（Workspace の API のエラーは、型が分類に無ければ HTTP の status で分類します）

## 現在の状態

プロバイダー `anthropic_workspace` のターンは、Claude Managed Agents のセッションへの 1 回の発言です（判断記録 #76、[ADR-0011](adr/0011-add-anthropic-workspace-provider.md)）。bot は発言を送り、イベントを読み、Hibana のツールが呼ばれたら実行して結果を返します。モデルを呼ぶループ、会話の保存、シェルとファイルの操作は Anthropic 側で動きます。

- **実 API で動かしたのは、Haiku 5.5・effort medium のセッションだけです**（2026-10-12、持ち主の承認のもとで AI が実行。「実 API での確認」）。Ultra なしでは、smoke の全項目と、bot 自身のターン（Discord は偽）が通りました。Haiku Ultra は、bot 自身のターン 1 回（workflow run が 1 つ始まって終わり、run のエージェントが bot のツールを呼ぶ）が通りました。Haiku Ultra のうち、budget で止まった run の扱い、run を止める発言、run が開いたままのセッションの削除は、実 API では動かしていません（smoke の `--ultra` の区間。実行を Claude Code の権限の仕組みが止めました）。Sonnet 5.5・Opus 5.5、実際の Discord を通したターンも、動かしていません。下に書く挙動のうち、その実行で観測していないものは、公開文書と SDK の型定義をもとに実装し、偽の応答でテストしたものです（「検証していない範囲」）
- 持ち主が決めたのは #76 の原文の 4 項目（プロバイダーとして足す、クラウドの作業領域を前提にする、既存のツールは入れられるものだけ入れる、Haiku Ultra に対応しモデルはほかは同じ）です。それ以外は、上限の既定値を含めて AI の案のまま実装しており、本人未確認です
- プリセットは 3 件です（`anthropic-workspace-haiku-5-5`・`-sonnet-5-5`・`-opus-5-5`。モデル名は `anthropic` と同じ）。Premium 以上が設定でき、最初は非公開です。Auto（Jev が選ぶ）のプリセットはありません。Auto Routing は `anthropic` だけのままです（#35）
- 上の 3 件のほかに、未公開のモデルのプリセットを 2 件、先に足してあります（`anthropic-workspace-opus-5-6`・`anthropic-workspace-fable-5-5`。`anthropic` 側にも `anthropic-opus-5-6`・`anthropic-fable-5-5`、#79）。4 件とも非公開です。モデル ID（`claude-opus-5-6`・`claude-fable-5-5`）は命名規則からの推定で、公開されたモデル一覧では確認できていません。実 API では一度も動かしていません。`anthropic` 側は料金表（`ANTHROPIC_PRICES`）に行がないので、行を足すまでは費用が「料金不明のリクエスト」として数えられます。Ultra は Haiku 5.5 だけのままです
- 公開するのは Web の `/models` です。設定 API を使わない bot（`WEB_API_URL` なし）には公開する手段が無いので、この 3 件は常に非公開・Premium 以上として扱います。Workspace より前の版が書いた `runtime_state.json`（一覧にこの 3 件の ID が無い）を読んだときも、起動のたびに 2 つの一覧へ足し直します。ほかのプリセットの一覧には触れません（`workspace-settings.test.ts`）。その構成で Workspace を使えるのは、`PROVIDER=anthropic_workspace` を bot の既定にしたときだけです（AI の案、本人未確認）
- 認証情報は `ANTHROPIC_WORKSPACE_API_KEY` だけです。`ANTHROPIC_API_KEY` は使いません
- 公式 SDK（`@anthropic-ai/sdk`、0.133.0 に固定）を、この経路だけで使います。ほかのプロバイダーの送受信は従来の実装のままです

## プロンプト

- **システムプロンプト**は `apps/bot/prompts/harness/workspace.md` です。Haiku Ultra のセッションでは、その後ろに `workspace-ultra.md`（workflow run をいつ始めるか、上限、止まった run の扱い）を足します。サーバー・利用者・モデルによらず同じ文字列で、セッションを作るときに渡します（100,000 字まで）。ファイルが無いときは、短い文面で続けずにターンを失敗にします
- **`<hibana_context>`**（人格、サーバーや個人の指示、会話の場所がチャンネル・スレッド・DM のどれか）は、利用者の発言の先頭に付けて送ります。セッションの最初の発言と、内容が変わったときだけです。Anthropic 側で会話が要約された後にも、もう一度付けます。スキルの一覧は入りません（この経路にスキルは無いため）
- 利用者の発言の末尾に `[date: YYYY-MM-DD]` を足します（UTC）
- 画像（png / jpeg / gif / webp、1 枚 3.7 MB まで）はデータとして発言に入れます。渡せない画像は送らず、その旨を 1 行足します。ほかの添付は、発言に付く URL から、モデルがコンテナの中で取得します
- 文面で名前を挙げる Hibana のツールは `send_file` だけです。作業ディレクトリのパスは書いていません（公開文書に記載が無いため、`pwd` で確かめるよう書いています）
- ターンを再開するとき（`/retry` と、起動時の自動の再開）は、セッションが既に受け取った発言を送り直さず、「中断された。済んだことを確かめてから続ける」という短い文を送ります。この文は「上の発言」を指すので、送る前に、チェックポイントが覚えている発言が、セッションに最後に送られた発言のままかを確かめます。違っていれば、本人の発言を新しい発言として送り直します。セッションにまだ送っていない発言がチェックポイントに残っているときは、短い文ではなく、その発言を送ります（「ターンの流れ」の「再開」）
- 前のターンの workflow run が開いたままのときは、その名前を注記として発言に付けます

## ツール

| 種類                                 | 中身                                                                                                                                                                                       | bot 自身のループのツールとの違い                                                                                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 組み込み（`agent_toolset_20260401`） | `bash`・`read`・`write`・`edit`・`glob`・`grep`・`web_fetch`・`web_search`。Anthropic のコンテナと Anthropic のサーバーで動く                                                              | 名前も説明も Anthropic のもの。**bot は 1 件ごとの権限チェックを挟めません**（permission policy は `always_allow`）。タイムアウトや出力の上限も Anthropic 側で決まる |
| `send_file`                          | コンテナの `/mnt/session/outputs/` の下のファイルを、Files API で取り出して Discord に添付する。25 MiB まで。書いた直後のファイルは、一覧に出るまで最長 30 秒待つ                          | サンドボックスの `send_file` とは別の定義。outputs の下のパスだけを受ける                                                                                            |
| `AskUserQuestion`                    | Discord のボタンで質問する                                                                                                                                                                 | この経路のための定義（名前と入力の形は Claude Code に合わせた）。実行は bot の質問の仕組み（`request_user_input` と同じ）。workflow run の中からは使えない           |
| 統合ツール（最大 74 個）             | Discord の読み取り 26 個と変更 31 個、bot の設定とプロフィール（読み取り 5 個、変更 6 個）、外部 MCP（`mcp_list_tools`・`mcp_call_tool`）、公開済みサイトの一覧・取り下げ・延長、`run_jev` | 名前に `mcp__` を付けない（custom tool の名前は `mcp__` で始められないため）。全件をセッションの作成時に渡す                                                         |

- 76 個は、サーバーの設定で使えるものが全部そろったときの数です。DM では 45 個、外部 MCP が無効なら 74 個、Jev もサイトの公開も設定していない bot では 72 個になります
- **入れていないもの**（持ち主の方針は「入れられるものは入れ、入れられないものは無理に入れない」）。どれも、bot の機械のサンドボックスにあるファイルや、bot のイメージに入ったプログラムに依るものです
  - サンドボックスのシェルとファイル操作、`download_file`・`download_attachment`: コンテナの中の組み込みツールとシェルで代える
  - `download_media`、`playwright_cli`、`video_edit`、画像生成の 3 個
  - スキル（スキルを読む・管理する 9 個）、`publish_site`
  - VPN の 4 個、自宅回線の 3 個、GitHub ログインの 3 個
  - Exa の 3 個: 組み込みの `web_search`・`web_fetch` を使う
  - 協調ツール、`Workflow`、Jev の行動選択モード（`run_jev_task`）
- ファイルのパスを取る引数（`edit_guild` の `icon_path`、`create_emoji`・`create_sticker`・`set_bot_avatar` の `path`）は一覧から外し、渡されたら断ります。これらのツールは bot の側で動き、コンテナのファイルを読めないためです。画像は URL で渡します
- 説明文を書き直したのは 9 個です（`send_file`・`set_bot_model`・`read_messages`・`edit_guild`・`create_emoji`・`create_sticker`・`set_bot_avatar`・`unpublish_site`・`extend_site`）。`tools/definitions.json` は、ほかのプロバイダーのターンに送る定義なので変えず、`apps/bot/src/workspace/tools.ts` の中で差し替えています。元の説明が、サンドボックスや、この経路に無いツールに触れているためです
- **一覧は話す人によらず同じ**で、サーバーの設定だけで決まります。その人が呼べるかどうかは、呼び出しのたびに `ToolRegistry.execute` を通して、そのターンの依頼者の権限・利用停止・引数のスキーマで判定します
- 読み取りと `run_jev` は同時に 6 件まで並行し、変更は 1 件ずつ実行します。質問は待ち行列の外で待ちます。同じ呼び出しは、連続 3 回目を断ります。結果は 40,000 字を超えると、先頭と末尾を残して切ります
- 組み込みの `web_search`・`web_fetch` は、`WEB_SEARCH_ENABLED`・`ANTHROPIC_WORKSPACE_WEB_ENABLED` のどちらかが偽のとき、またはサーバーの exa が off のときに外します。`TOOLS_ENABLED=false` なら、組み込みツールも含めて何も渡しません
- Jev の行動選択モードは、この経路でも設定にかかわらず使いません
- 進捗表示は、チャンネルの全員に見えるメッセージ 1 つを書き換えていくものです。依頼した人だけでなく、そのチャンネルを読める全員に、次のものが見えます
  - モデルがツール呼び出しの前に書いた文。そのまま出します（約 1,900 字で切ります）
  - ツール呼び出しから作った 1 行。`read`・`write`・`edit` のパス、`glob`・`grep` のパターン、`web_search` のクエリ、`web_fetch` のホスト名、`send_file` のファイル名が、120 字まで入ります。ほかの Hibana のツールは名前だけです。`bash` のコマンドの中身は出さず、固定の文にします（コマンドには、モデルが扱っていた内容が何でも入りうるため）
  - 固定の文（同時実行の枠の待ち、モデルへのリクエストの再試行）と、workflow run のエラー（API が書いた文面を 120 字まで）
- workflow run は、run ごとに別のメッセージで状態を出します。run が開いている間にモデルが止まるときに書いた文も、進捗に出ます（[Haiku Ultra](#haiku-ultra)）

## セッションと作業領域

- セッションは**チャンネルごとに 1 つ**です（スレッドと DM もそれぞれ 1 つ）。会話とコンテナは Anthropic 側にあります。ほかのプロバイダーのサンドボックスは、サーバーの通常のチャンネルどうしでファイルを共有しますが、この経路では共有しません
- **同じチャンネルのターンは、発言した人によらず 1 つずつ**順に実行します。bot がチャンネルごとに持つキューによるもので、ほかのプロバイダーのターンも同じです（別の人の発言も `/retry` も、同じキューに並びます）。1 つのセッションに 2 つのターンが同時に入ると、互いのイベントを読み、相手のツール呼び出しに別の人の権限で答えてしまいます。そのため、同じチャンネルのターンが動いている間に 2 つ目が渡されたら、何も送らずに失敗にする歯止めも置いています（キューを通る限り、ここには届きません。`workspace-turn.test.ts` の「one channel, one turn at a time」）
- どのチャンネルがどのセッションを使うかは、`conversations.db` の表 `workspace_sessions` に保存します。片付けを待つセッションは `workspace_disposals` にあります（どちらも追加だけ。[ADR-0008](adr/0008-keep-conversations-across-restarts.md) の規則）
  - この 2 つの表には、作った後で列を 1 つずつ足しています。`workspace_sessions.lease_settled`（残っている lease の印）と `workspace_disposals.allowed_cents`（片付けに回った時点で、まだ数えていなかった枠）です。使い方は「上限と費用」にあります
  - `CREATE TABLE IF NOT EXISTS` は既にある表を変えないので、bot は `conversations.db` を開くたびに `PRAGMA table_info` で列を確かめ、無い列だけを `ALTER TABLE … ADD COLUMN` で足します。列が空の行は、今までどおりに読みます（`workspace-sessions.test.ts` の「a file from before a lease's settlement was kept gains the two columns, and its rows read as they did」。足し方は AI の案、本人未確認。代案は、このブランチで作った表なので `CREATE TABLE` の文に入れる形です）
- エージェント 2 つ（委譲なしの plain と、dynamic workflows を有効にした ultra）と、environment 1 つを使い回します。起動時には作らず、最初のターンで作って、ID を `HIBANA_DATA_DIR/anthropic_workspace_resources.json` に保存します。モデル・effort・システムプロンプト・ツールは、セッションを作るときに上書きして渡します。effort は常に明示します（`none` は `low` にします）
- **セッションの設定は、作ったときに固定されます。** プロンプトやツールの説明を直して配信しても、既にあるセッションは前の内容のまま動きます。ツールの一覧が変わっていることは、ログに `Workspace session keeps an older tool list` と出るだけです。web 検索の有無も同じです。`run_jev` の `images`（#83）も、追加より前に作ったセッションには無く、そのセッションでは画像を渡せません
- セッションを作り直すのは次のときです

  | きっかけ                                                                                                                                                   | 前のセッション                                                                            |
  | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
  | `/clear`、チャンネルやスレッドの削除                                                                                                                       | delete（会話も作業ファイルも消える。workflow run が開いたままだと拒否されうる。「限界」） |
  | サーバーのモデル・effort・サブエージェントのモードの変更（そのサーバーの全チャンネル）、話す人の個人設定などで会話のキーが変わったとき、スレッドの期限切れ | archive（同上）                                                                           |
  | Anthropic 側でセッションが無くなっていた（発言を送る前に分かったとき）                                                                                     | 1 回だけ作り直し、利用者に「新しい会話として始めます」と伝える                            |

  発言を送った後にセッションが無くなったときは、作り直しません（同じ依頼を 2 回実行しないため）。そのターンは失敗になります

- **bot がサーバーから外されても（kick）、そのサーバーのセッションは作り直しも片付けもしません。** 行と、Anthropic 側の会話・作業ファイルは残ります（「限界」）
- **`/clear` は作業ファイルも消します。** ほかのプロバイダーの `/clear` は会話だけを消し、サンドボックスのファイルは残すので、意味が違います（#76 の 6。本人の判断待ち）
- コンテナの中身は、**セッションの作成から 30 日で失われます**。使っていても延びません（公開文書の記述）。`/context` の `workspace.container_until` に、作成から 30 日後の日時を目安として出します
- 手元の会話履歴には、利用者の発言と最終の返信だけを記録として残します（`/context` 用）。モデルには送りません
- 片付けは、先にセッションの budget を下げてから delete / archive します。失敗したら次の掃除（60 秒ごと）でやり直し、5 回失敗したものは次の起動まで待ちます。利用額の台帳を読めていない間は、budget を下げるところまでで止め、delete / archive はしません（「上限と費用」）
- チェックポイントだけが覚えているセッション（会話の保存先が無い bot が、ターンの途中で落ちた後など）は、そのターンを再開するときに片付け待ちへ入れて止め、archive します（「ターンの流れ」の「再開」）

## Haiku Ultra

サブエージェントのモードが ultra で、モデルが Workspace の Haiku 5.5 のときだけ、セッションを ultra のエージェントで作ります。エージェントは、Managed Agents の dynamic workflows（複数のエージェントを並行に動かす workflow run）を始められます。Workspace のほかのモデルと、on / multi は、委譲なしで動きます（保存値は残ります）。

既存の Ultra（[Ultracode](ultracode.md)）と名前は同じですが、中身は別です。

|                                    | Ultra（Ultracode。ほかのプロバイダー）                           | Haiku Ultra（workspace 経路）                                                                                                                                                      |
| ---------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 働く条件                           | モードが ultra（モデルを問わない）                               | モードが ultra で、モデルが Workspace の Haiku 5.5                                                                                                                                 |
| 仕組み                             | Hibana の Workflow ツール（bot の中の QuickJS で動くスクリプト） | Managed Agents の dynamic workflows（Anthropic 側で動く）                                                                                                                          |
| effort                             | xhigh に固定                                                     | 保存値のまま                                                                                                                                                                       |
| 使い方                             | 実質的な依頼には毎回                                             | 条件つき。プロンプトに「分けられる大きな仕事のときだけ」「同時に開く run は 1 つまで」と書いてある。始めるかどうかはモデルが決める                                                 |
| キーワード `ultracode`             | その回だけ有効になる                                             | 効かない                                                                                                                                                                           |
| 上限                               | 同時実行数と体数。金額の上限は無い                               | 1 ターンの金額（既定 $3）と時間（既定 60 分）。同時 64 スレッドなどは Anthropic のサーバーが決める                                                                                 |
| ターンとの関係                     | ターンが終われば止まる                                           | run はセッションの中で動き続ける。bot は run が終わるまで返信を待つ                                                                                                                |
| run の中から使える Hibana のツール | 送信・公開・設定の変更を断る                                     | 読み取りの 26 個だけ（Discord の読み取りのうち、管理の権限が要る 7 個を除いた 19 個と、設定・サイト・MCP の一覧の 7 個）。投稿・ファイルの送信・設定の変更・質問・`run_jev` は断る |

- `WORKFLOWS_ENABLED`・`SUBAGENT_ENABLED`・`TOOLS_ENABLED` のどれかが偽なら、Haiku Ultra も働きません（plain のセッションになります）
- plain と ultra はエージェントが別なので、Ultra を切り替えるとセッションを作り直します
- `/switch ultra:on` を、Haiku Ultra にならない組み合わせ（Haiku 5.5 以外、Multi-Agent が on、ワークフローが無効）で使うと、設定を保存したうえでその旨を返します
- 上限や追加発言で止めた run は、開いたまま残ります。`user.interrupt` はエージェントのターンを止めますが、run を終わらせません（公開文書の記述）。次の発言には「前のターンの run が開いている」という注記が付き、続けるか止めるかはモデルが発言に従って決めます
- run が開いている間は、モデルが止まってもターンは終わりません。その間にモデルが止まるときに書いた文は、返信ではなく進捗として、その場で出します（プロンプトが「run を始めたら、何をしているかを 1 行書いて止まる」と指示しています。進捗に同じ文を 2 回は出しません）。run が止まったまま残ってターンが終わるときは、その文が返信の本文になります（進捗に出した文が、返信にもう一度出ます。「限界」）
- run の中のエージェントが Hibana のツールを呼ぶときは、**その run を始めた人**の権限で判定します。別の人のターンの間に届いた呼び出しは、読み取りも断ります。どの run のスレッドか、またはその run を誰が始めたかが分からない呼び出しも断ります（モデルに返す文は別で、「誰が始めた run か、ここでは分からない」と伝えます）
- スレッドがどの run のものかは、スレッドが作られたときのイベント（`session.thread_created`）でしか分かりません。続けた run は、前のターンで作られたスレッドからツールを呼ぶので、開いた run を行が覚えているターンは、発言を送る前にイベントの一覧（run の開始と終了、スレッドの作成）を読み、開いている run と、スレッドと run の対応を作り直します。一覧は新しい順に読み、行が覚えている最も古い run の開始で止めます（セッションの全部の run のスレッドを、毎ターン読み直さないため。読み方は AI の案、本人未確認）
  - 読むのは 10,000 件までです。そこで打ち切ったときは、行が覚えている run をそのまま使い、対応は新しい側のスレッドだけになります
  - 行が run を覚えていないとき（run を始めたターンの途中でプロセスが落ちた後）は、対応を作り直せず、その run のスレッドからの呼び出しは、始めた本人のターンでも断られます

## ターンの流れ

同じチャンネルのターンは 1 つずつです（「セッションと作業領域」）。

1. 手元で確かめる: 入力長（いちばん新しい発言 1 件の長さ。「再開」）、1 日と月の利用額の枠。足りなければ API を呼ばずに定型文を返す。再開（`/retry`、起動時の自動の再開）も同じ枠で確かめる
2. bot 全体の同時実行の枠を待つ。待つ間は進捗に 1 行出す
3. セッションが無ければ作る（budget つき）
4. セッションを読む。使用済みなのに額（list cost）を報告していないセッションは、ここで失敗にする（「上限と費用」）。前の作業が残っていそうなセッション（idle でない、run が開いている、budget に達して止まっている、取り上げ前の発言が残っていると分かった）には、先に `user.interrupt` を単独で送る
5. セッションの budget を「消費済み + このターンの枠」に上げ、ストリームを開き、発言を 1 回だけ送る。送信の結果が分からないときは、イベントの一覧で探す。見つからなければ失敗にし、そのターンの中では送り直さない（発言はチェックポイントに残り、まだ送っていない発言として、次の再開か発言で送られる。「再開」）
6. イベントを読む。Hibana のツールの呼び出しは、届いた時点で実行して 1 件ずつ結果を返す。ストリームが切れたら開き直し、イベントの一覧で追いつく（同じイベントは 1 回だけ処理する）
7. セッションが `end_turn` で idle になり、開いている run が無ければ完了。run が止まったまま残っているときは、15 秒待ってから、その旨を添えて終える
8. どの終わり方でも、budget を「消費済み + 1 セント」に下げる。budget に達して止まったセッションの budget は変えない（変えると、止まっていたスレッドが 1 リクエストずつ進むため）
9. セッションの累積 usage の差分を、利用額の台帳に足す。額を報告しないセッションの枠をどこで数えるかと、ターンの後に lease を残す場合は、「上限と費用」にある

下の各項は、公開文書と SDK の型定義から組んだものです。実 API で通ったのは、Haiku 5.5 のセッションで smoke が見た範囲です（「実 API での確認」の「2026-10-12 の実行」）。workflow run にかかわる項のうち、実 API で通ったのは、bot 自身の Haiku Ultra のターン 1 回が通った範囲（run の開始から終了まで、run のエージェントからのツール呼び出しとその結果）だけです。挙動の選び方は AI の案で、本人未確認です。

**どこからがこのターンか**

- idle で、run も開いておらず、budget にも達しておらず、取り上げ前の発言が残っているとも分かっていないセッションは、発言を送った後に届くイベントがすべてこのターンのものです
- それ以外（手順 4 で interrupt を送ったセッション）は、前の作業のイベントがまだ届きます。ストリームに自分の発言が「処理済み」（`processed_at` つき）として届くまでのイベントは、前の作業のものとして扱います。イベントの一覧が先に発言を処理済みと示しても、ストリームの順序のほうを正とします（一覧は、ストリームで読み終えた位置より先に進んでいることがあるため）
- **取り上げ前の発言が残っているセッション**（新しいセッションで、最初の発言が取り上げられる前に同じ人が言い直したときなど）は、status が idle と読めても、「それ以外」の側として扱います。発言は送った順に取り上げられる、と公開文書から読んでいるためです（「queued behind earlier events」）。そのまま送ると、前の発言への出力が、このターンの返信になります。先に interrupt を送り、自分の発言が処理済みとして届くまでの出力は、前の作業のものとして捨てます（**AI の案、本人未確認**。代案は「何もせず、idle のセッションとして扱う」）
  - 残っていると分かるのは、額の報告が無くて、発言の一覧を読んだときだけです（「上限と費用」）。額を報告しているセッションでは調べません（毎ターン、一覧のリクエストが 1 回以上増えるため。「限界」）
- 前の作業のツール呼び出しは実行せず、「前のターンの呼び出しなので実行していない」という結果を返して閉じます（セッションがその呼び出しを待ち続けないため）
- ストリームが発言を処理済みとして届けない場合の保険として、発言が届く前に、ツール呼び出しか、セッションの停止（呼び出し待ち以外の idle）が来たら、イベントの一覧でそのイベントの位置を確かめます。一覧が発言より後に置いたものだけを、このターンのものとして処理します

**budget で止まった後の次の発言**

budget の定型文は「続けるには、もう一度メッセージを送ってください」と案内するので、止まったセッションへの次の発言は、普通の続け方です。公開文書によれば、budget に達して止まっている間の `user.interrupt` はどのスレッドも止めず（すべて止まっているため）、budget を上げると、止まっていた作業が自動で再開します。そこで、budget に達していたセッションには次の順に送ります。

1. `user.interrupt` を単独で送る。止まっていた run を、budget を上げた後も止めたままにするためです（interrupt で止めた run は、budget を上げても再開しない、と公開文書にあります）
2. budget を上げる。止まっていた前の作業が再開します
3. 発言を `[user.interrupt, user.message]` の 1 リクエストで送る。再開した前の作業を止めてから、この発言を始めさせます

- 再開した前の作業が出したもの（文、ツール呼び出し）は、このターンの返信に使いません。**「止めて捨てる」は AI の案で、本人未確認です**（代案は「このターンの成果として見せる」）。引き上げから interrupt が届くまでに前の作業が使った分は、このターンの枠から出ます
- 発言の送信が 400 で断られたとき（セッションが前のターンのツール呼び出しを待っている）は、interrupt を単独で送り、残った呼び出しを閉じてから、発言だけを 1 回送り直します
- 発言が取り上げられる前に、セッションが budget に達して止まったとき（再開した前の作業が枠を使い切った）は、時間の上限まで待たずに、budget の定型文で終えます。**その発言はセッションのキューに残り**、次の発言のターンで先に処理されることがあります（その分の費用がかかります）
- 同じく取り上げられる前に、セッションがリトライを使い切って止まったとき（`retries_exhausted`）は、15 秒待っても動き出さなければ、ターンを失敗にします

**ストリームを開き直したとき**

- イベントの一覧を新しい順に読み、処理済みになった自分の発言まで戻って、その後のイベントを古い順に処理します
- 一覧に、自分の発言が処理済みとして無いとき（まだキューにある）は、**一覧のイベントを 1 件も再生しません**。そこにあるのは前のターンのもので、再生すると、前の返信をこのターンの返信にし、答えの付いていない前の呼び出しを、今の話者の権限で実行してしまうためです。前の作業が残っていたセッションでは、答えの付いていない呼び出しを閉じるだけにします。発言より前の、別の処理済みの `user.message` に当たったら、そこで読むのを止めます
- 例外は 1 つです。発言が処理済みと分かっていて、10,000 件読んでもそこまで戻れない大きなターンは、読んだ分を再生します（この枝にテストはありません）
- 送信の応答から発言の id が得られなかったときは、本文の一致で探します。一覧では、ストリームを開いた時刻より後に処理されたものだけを、自分の発言と認めます（同じ文面の古い発言を取り違えないため）
- 一覧だけが発言の位置を決めた接続では、届くイベントの時刻（`processed_at`）を発言の時刻と比べ、前のものを前の作業として扱います。同じ時刻のものは、このターンのものとして扱います（前の作業の最後のイベントが同じ時刻だと、取り違えます。「限界」）

**ツールの結果が届かなかったとき**

- 結果の送信が失敗したとき（接続の失敗や 5xx。SDK のリトライの後）は、結果を持っておいて送り直します。ツールは再実行しません。送り直すのは、失敗の 30 秒後（また失敗すれば、その 30 秒後）、セッションが「その呼び出しを待っている」と知らせてきたとき、ストリームを開き直したとき、ターンを止めるときです
- 結果が 400 で断られたときは、「実行したが、結果を受け取ってもらえなかった。繰り返す前に確かめること」という error の結果を 1 回だけ送ります。それも 400 なら捨てます。公開文書の手順（スレッドの一覧で、その呼び出しのスレッドが `terminated` なら捨てる）とは違う形です。遅すぎた結果なら 2 回目も 400 で捨てられ、内容が受け取られなかっただけなら、セッションの待ちが解けます
- 前の作業が残した、答えの付いていない呼び出しを閉じる結果は 2 種類です（どちらもモデルに見える英語の文です）
  - このターンがストリームを開いた後に作られた呼び出し: 「前のターンの呼び出しなので実行していない」。誰も実行していないことが分かっているためです
  - それより前に作られた呼び出し（一覧で見つけたもの）: 「前のターンが開いたまま残した。実行されたかはここでは分からないので、繰り返す前に確かめること」。前のターンが実行した後、結果を届けられずに終わった可能性があるためです

**本文なしで終わったとき**

- セッションが `end_turn` で終わったのに本文が無く、このターンでチャンネルに何も届いていないときは、「返信の本文がないまま、このターンが終わりました。必要であれば、もう一度メッセージを送ってください。」を返信にします。自動では送り直しません（もう 1 ターンぶんの費用がかかるため）
- ターンは完了として扱います。費用は台帳に足し、チェックポイントは消えます。このターンでファイルを送っていれば、それが答えなので、何も足しません

**途中で止まる場合**

- **同じ人の追加発言**: `user.interrupt` を送り、セッションが止まるのを待ってターンを閉じます。その間に溜まった発言は 1 つにまとめて、次のターンになります。閉じたターンの発言が、まだ取り上げられていないと分かったときは、次のターンがそれを前の作業として扱います（「どこからがこのターンか」）
- **bot の再起動**: interrupt と budget の引き下げを試み（8 秒まで）、チェックポイントを残します。起動後は、残ったセッションの片付けを最初に始めます（Discord のコマンド登録や、サーバーごとの初期化より前。片付けは Discord を使わないので、起動の残りが失敗しても走ります）。Workspace のターンは、その片付けが済んでから、**1 回だけ**自動で再開します。もう一度止まったら `/retry` を待ちます（再起動を繰り返す bot が、同じ作業を何度も始めないため）
- **利用停止になった人、bot を無効にしたサーバー**: イベントごと（と 30 秒ごと）に確かめ、該当したら止めて、返信しません
- **`/clear`**: ターンを止め、失敗の定型文は出さず、セッションを delete します。同じチャンネルで順番を待っていた発言は消えず、クリアの後に、新しい会話として実行されます

**再開（`/retry` と、起動時の自動の再開）**

- チェックポイントは、終わらなかったターンのために本人が書いた発言を溜めていきます（次の発言も、その後ろに足されます）。発言がセッションに受理されると、チェックポイントに再開の印を残します。印が持つのは、セッション、送った発言の id、そのときの上限、始めた時刻、発言なしで再開した回数と、**溜まった発言のうち何件目までが済んだか**（`sent`）です。「済んだ」は、セッションが受け取ったか、長さのために送らなかった（下の項）かのどちらかです
- 溜まった発言には、セッションに届いていないものが混ざりえます。発言が受理された後でターンが失敗し、次の発言のターンが、発言を送る前に失敗した場合です（budget の引き上げやセッションの読み取りの失敗。チェックポイントは、2 つの発言と、1 つ目までを指す印になります）。失敗の定型文は「`/retry` または次のメッセージで再開できます」と案内するので、**まだ送っていない発言は、そのどちらでも送ります**
  - 発言なしの再開（`/retry`、起動時の自動の再開）では、短い文の代わりに、まだ送っていない発言だけを、1 つの発言として送ります。セッションが既に受け取った発言は送り直しません
  - 次に本人が発言したときは、まだ送っていない発言を前に付けて、1 つの発言として送ります
  - **1 つにまとめると入力長の上限を超えるときは、新しいものから順に、収まるだけを送ります**（AI の案、本人未確認。代案は「合わせた長さで断り、定型文に、前に送れなかった発言を含むと書く」）。上限内の発言が、その前に書いた発言のせいで「長すぎます」と断られないようにするためです
    - いちばん新しい 1 件は必ず送ります。その前の発言は、新しい側から続けて収まる分だけを付けます（つなぎの空行も数えます。間の 1 件を飛ばして、さらに古い発言を送ることはしません）。画像も、送る発言に付いていたものだけです
    - 送らなかった件数は、そのターンの返信の後ろに 1 行で付けます。「最後のメッセージより前の N 件は、合わせると Anthropic Workspace に送れる M 文字を超えるため、送っていません。必要であれば、もう一度送ってください。」（M は入力長の上限）
    - 送らなかった発言は、済んだものとして扱います（印の `sent` に数えます）。後のターンが、頼まれずに送り直すことはしません
    - 断るのは、いちばん新しい 1 件だけで上限を超えるときだけです。定型文の文字数は、その 1 件の長さです
    - この 1 行は、返信と一緒に出すものです。本文なしで終わったターンと時間切れのターンでは、それぞれの定型文の後ろに付きます。同じ人の言い直しで止まったターンでは、この 1 行だけが単独の発言として出ます。出ない終わり方もあります（利用停止で止めたターン、発言を送った後で失敗したターン。「限界」）
  - どちらも、新しい発言と同じ扱いです。新しい枠と新しい時間の上限で動き、入力長・台帳・1 日と月の枠で確かめます。断られたとき（いちばん新しい 1 件が長すぎる、上限に達している、台帳を読めていない）は、定型文が出てチェックポイントが消え、まだ送っていなかった発言も一緒に消えます
  - 発言なしの再開は、この形でも「再開 1 回」と数えます。起動時の自動の再開では、まだ送っていなかった発言（最大 2 時間前のもの）が、新しい枠で自動的に送られます（1 回だけ）
  - この形では、下の「セッションに最後に送られた発言」の確かめをしません（短い文と違い、「上の発言」を指さないため）。同じチャンネルで別の人の発言が間に入っていても、送るのは、まだ送っていない発言だけです（**AI の案、本人未確認**。代案は「発言なしの再開では常に確かめ、違っていれば溜まった発言を全部送り直す」で、1 リクエスト増えます）
  - `sent` の無い印（この数を持つ前に書かれたチェックポイント）は、今までどおり「新しい発言のほかは、すべて受け取られている」として読みます。`sent` が溜まった発言の数より大きくても、新しい発言は必ず送ります
- 再開も、新しい発言と同じく、台帳と 1 日・月の枠で確かめます。台帳を読めていなければ断り、残りが足りなければ 1 日・月の定型文で断ります（API は呼びません）。断ったターンは完了として扱われ、チェックポイントは消えます（枠が戻った後は、`/retry` ではなく新しい発言が要ります）。起動時の自動の再開が断られたときも、チャンネルに定型文が出ます
- 新しい発言も、まだ送っていない発言も無い再開だけが、短い文で続きます。下の 3 項（上限、時間、最後に送られた発言の確かめ）は、この形の再開のことです
- 再開が使えるのは、最初に始めたときの上限（消費済み + そのときの枠）までで、新しい枠は足しません。1 日・月の残りがそれより少なければ、残りの分までに切り下げます
- 時間の上限は、最初に始めた時刻から数えます
- 再開の前に、セッションに最後に送られた `user.message` を読み（1 リクエスト）、チェックポイントが覚えている発言と同じかを確かめます。同じなら、「中断された。続けて」の短い文を送ります。違う（同じチャンネルで、別の人の発言が間に入った）か、チェックポイントに発言の id が無ければ、**本人の発言を新しい発言として送り直します**（溜まった発言の全部を、1 つの発言として。入力長の上限を超えるときは、上の規則で、新しいものから収まるだけを送り、送らなかった件数を返信に付けます）。短い文は「上の発言」を指すので、そのまま送ると、別の人の依頼を、再開した人の権限で続けることになるためです。送り直したターンは、新しい枠と、新しい時間の上限で動きます（起動時の自動の再開でも同じです。代案は「断る」「起動時だけ `/retry` を待つ」）
- 確かめるリクエストが失敗したとき（セッションが無い場合を除く）は、何も送らずにターンを失敗にします
- チェックポイントのセッションが、そのチャンネルの今のセッションでないとき（会話が作り直された、会話の保存先が無い bot が落ちた）は、今のセッション（無ければ新しく作ります）に、本人の発言を送り直します。発言なしの再開は、送り直しになっても「再開 1 回」と数えるので、自動の再開は 1 回で止まります
- そのとき、チェックポイントのセッションが、表にも片付け待ちにも無ければ、1 回読みます。archive 済み・terminated・404 なら、何もしません（片付けが済んだ後の姿で、もう費用は使えないため）。それ以外（読めなかった場合を含む）は、片付け待ちに入れて止め、archive します。そのセッションが使った額は、累計の全額を台帳に足します（前のプロセスが記録していた分を、二重に数えることがあります。上限には安全側です）。ログに `Workspace session of an unfinished turn is in no row; it is stopped and all it has used is counted` が出ます

## 上限と費用

既定値と範囲は AI の案で、本人未確認です（#76 の 2〜4）。環境変数で変えます。範囲の外の値は、起動時にエラーにします。

| 上限                         | 環境変数                                                 | 既定             | 達したとき                                                                                                                                                                                                                 |
| ---------------------------- | -------------------------------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 ターンの金額               | `ANTHROPIC_WORKSPACE_TURN_BUDGET_USD`（0.05〜100）       | 1                | セッションが止まり、「このターンの費用の上限（$1.00）に達したため、ここで止めました。…」と返す                                                                                                                             |
| 同、Haiku Ultra              | `ANTHROPIC_WORKSPACE_ULTRA_TURN_BUDGET_USD`（0.05〜100） | 3                | 同上                                                                                                                                                                                                                       |
| 1 日の金額（bot 全体。UTC）  | `ANTHROPIC_WORKSPACE_DAILY_BUDGET_USD`（0.01〜10000）    | 5                | ターンを始めずに「…1 日の利用額の上限に達しているため、実行しませんでした。…」と返す                                                                                                                                       |
| 月の金額（bot 全体。UTC）    | `ANTHROPIC_WORKSPACE_MONTHLY_BUDGET_USD`（0.01〜100000） | 50               | 同、「今月の利用額の上限」                                                                                                                                                                                                 |
| 1 ターンの時間               | `ANTHROPIC_WORKSPACE_TURN_TIMEOUT_MS`（1〜86400000）     | 1200000（20 分） | 中断して「このターンの時間の上限（20 分）に達したため、中断しました。…」と返す                                                                                                                                             |
| 同、Haiku Ultra              | `ANTHROPIC_WORKSPACE_ULTRA_TURN_TIMEOUT_MS`（同）        | 3600000（60 分） | 同上                                                                                                                                                                                                                       |
| 同時に動くターン（bot 全体） | `ANTHROPIC_WORKSPACE_MAX_CONCURRENT`（1〜64）            | 2                | 空くまで待つ                                                                                                                                                                                                               |
| 1 回の発言の長さ             | `ANTHROPIC_WORKSPACE_INPUT_MAX_CHARS`（1〜1000000）      | 60000            | いちばん新しい発言 1 件が超えるときは、送らずに「メッセージが長すぎます…」と返す。まだ送っていない発言と合わせて超えるときは、新しいものから収まるだけを送り、送らなかった件数を返信に付ける（「ターンの流れ」の「再開」） |

- 金額は、セッションが報告する **list cost**（公開単価での額）です。値引きや請求の単位とは一致しないことがあります。内訳は、モデルのトークン、セッションが `running` の間の $0.08 / 時、web 検索 $10 / 1,000 回です（料金ページの記述）
- 1 ターンの金額の上限は、Anthropic 側の session budget で置きます。bot が落ちても効きます。budget はモデルへのリクエストの間で判定されるので、**上限をまたいだリクエストは最後まで実行されます**。workflow run では、動いているスレッドごとに 1 リクエストぶん超えることがあります（公開文書の記述）
- 1 ターンの上限は「セッションが使った額 + このターンの枠」として置くので、**使用済みなのに額（list cost）を報告しないセッションでは、ターンを始めません**（使った額を 0 から数えることになるため）。ターンは発言を送る前に失敗になり、表示は「プロバイダとの通信を再試行しましたが、応答を完了できませんでした。（送信時・list_cost_missing）」です。「使用済み」と見なすのは、次のどれかのときです（線引きは AI の案、本人未確認）
  - セッションが、トークンや稼働秒数などの使用量を報告している
  - bot が、そのセッションの使用量を以前に数えている（行に累積値がある）
  - セッションに、処理済み（`processed_at` つき）の `user.message` がある。上の 2 つに当たらないときに、発言の一覧（`user.message` だけ、API の既定の順）を読んで確かめます
    - 1 ページ目で止めず、**処理済みの発言が見つかるか、一覧が尽きるまで**読みます。見つかれば、そこで読むのをやめて断ります。一覧の並びや 1 ページの件数が見込みと違っても、処理済みの発言が一覧に載っている限り、「未使用」とは読みません（`workspace-runner.test.ts` の「the message that was taken up is looked for past the first page of the list」）
    - 10,000 件読んでも、または一覧のリクエストを 20 回送っても決まらないときは、使用済みとして断ります。読まなかった部分に、処理済みの発言があるかもしれないためです。リクエストの回数も数えるのは、イベントの無いページに「次のページ」が付く応答だと、件数が進まないためです（`workspace-runner.test.ts` の「a list whose pages never end is given up after a fixed number of requests」）。断る側に倒すことと、20 回という値は、AI の案で本人未確認です（20 回に根拠はありません。代案は「取り上げ前の発言あり」として始めることで、その場合、読まなかった部分に処理済みの発言があると、使った額を 0 から数えます）
    - 一覧のリクエストは、発言が 1 件も無い新しいセッションでは 1 回、最初に読んだページに処理済みの発言があれば 1 回です。増えるのは、取り上げ前の発言が何ページも並ぶセッションで、一覧が尽きるまで、または処理済みの発言が載っているページまで読みます（多くても 20 回）。1 ページの件数は確かめていません。ページとページの間で、ターンの時間の上限を見ます。過ぎていれば読むのをやめ、ターンは何も送らずに時間切れで終わります
  - 取り上げ前の発言がキューにあるだけなら、使用済みとは見なしません。新しいセッションは、最初の発言が取り上げられるまで額を報告しない、と見ているためです（SDK の型のコメント「Absent until cost tracking is available」による。2026-10-12 の実行では、作成直後のセッションから額が 0 セントとして報告されたので、この分かれ道には入っていません）。新しいセッションで、最初の発言が取り上げられる前に同じ人が言い直しても、2 つ目のターンは始まります。残っていた発言は、前の作業として扱います（「どこからがこのターンか」）
- 1 ターンの 2 つの上限の下限が 0.05 なのは、枠が 5 セント未満のターンを始めないためです（モデルへの 1 リクエストが、それより高くなりうるため）。それより小さい値を受け付けると、すべてのターンを「1 日の利用額の上限」の定型文で断ることになるので、起動時のエラーにしています。1 日と月の上限は 0.01 まで下げられます。**今の環境に 0.05 未満の値があると、bot は起動しなくなります**（下限の値は AI の案、本人未確認。実際の `bot.env` の値は確かめていません）
- 1 日と月の枠は、bot の台帳（`HIBANA_DATA_DIR/anthropic_workspace_usage.json`）で判定します。実行中のターンに渡した枠と、ターンが終わっても budget を下げられていないセッションの枠（行に残った lease）は、使い切るものとして先に引きます（予約）。印の付いた lease は、予約に入れません（下の項）。残りが 5 セント未満なら、ターンを始めません。台帳を読めていない間は、Workspace のターンを、新しい発言も再開も断ります
- **1 日と月の判定には、報告された額より多い額を使います**（AI の案、本人未確認）。セッションが報告する額は 1 セント単位の四捨五入なので（公開文書の記述）、0.5 セントに届かないセッションは 0 と報告されます。短いセッションを作り続けると、報告された額だけでは上限に届きません。そこで、判定にだけ次の額を足します
  - セッションを 1 つ作るたびに 1 セント（普通のセッションも、1 セント多く数えることになります）
  - トークンや稼働秒数などの使用量が増えたのに、額（list cost）が報告されなかった区間には、そのセッションに渡していた枠の全額。枠を数えるのは、この「使用量の報告があるのに、額の報告が無い」区間だけです。**1 つの枠を数えるのは 1 回だけ**で、その使用量を最初に読んだ処理が数えます。読む処理は 3 つあります
    - ターンの精算: そのターンの枠
    - 掃除（ターンの後に残った lease を、60 秒ごとに見る処理）: lease に残っている枠（lease の上限から、台帳が数えた額を引いたもの）
    - 片付け（会話が終わったセッションの delete / archive）: 行が片付け待ちに回った時点で、lease に残っていた枠。lease そのものは片付け待ちに持って行かないので、この額だけを `workspace_disposals.allowed_cents` に写します（再起動をまたいで残ります）
  - 枠を数え終えたことは、lease の印で覚えます（`workspace_sessions.lease_settled` の `counted`）。ターンか掃除が枠を数えた後に budget を下げられなかったとき、lease は行に残りますが（budget がまだ上がっているため）、後の掃除と片付けは同じ枠を数え直しません。使用量がさらに増えても同じです。`counted` の印は、その lease が続く間は外れません
  - **数え終えた枠は、予約に重ねません。** `counted` の lease は、1 日と月の枠から先に引く分（上の予約）に入れません。判定用の額に入った枠を、予約としてもう一度引くことになるためです
  - **使用量の報告がまったく無かった区間には、何も足しません**（何も使っていないものとして扱います）。発言がセッションに受理されていても同じです。発言が取り上げられる前に、`/clear` された、同じ人が言い直した、時間切れになった、というターンがこれに当たります。受理されただけで枠の全額を数えると、既定の上限（1 ターン $1、1 日 $5）では、そういうターン 5 回で、その日の Workspace のターンが全員に対して断られるためです（`/clear` は誰でも使えます）。「取り上げ前のセッションは、使用量を何も報告しない」は前提で、実 API では確かめていません（「検証していない範囲」）
  - **使用量も額も見えないまま終わったターンの枠は、捨てずに残し、後から使用量が出たときに数えます。** 発言は取り上げられていたのに、ターンの最後の読み取りに使用量が間に合わなかった、という場合があるためです（AI の案、本人未確認）
    - そういうターンは、budget を下げ終えた後も、lease を `lowered` の印つきで行に残します。次の掃除（lease が残っている間、60 秒ごとに走ります）がセッションをもう一度読み、使用量（額なし）が出ていれば、枠を 1 回数えます。何も出ていなければ、何も足しません。どちらの場合も、セッションを読めたら、その掃除で lease を外します（budget を 1 セント単位まで下げ直せなくても外します。ターンが下げ終えているためです。読めなかったときだけ、次の掃除に回ります）。発言を送る前に終わったターンでも、budget を下げ終えていて、使用量も額も見えていなければ、同じ扱いです（掃除の読み取りが 1 回増えます。コードの読み取りによる）
    - 掃除より前に会話が終わったとき（`/clear`、モデルの変更など）は、片付けが読み、同じ規則で数えます。ターンが例外で終わって、印の無い lease が残っていたセッションも同じです。片付けは待たずに、会話が終わった直後に読みます
    - `lowered` の lease も、予約には入れません。budget は下げ終えていて、セッションはそれ以上使えないためです。予約に入れると、1 日の残りが少ないときに、同じ人が言い直した 2 つ目のターンが、1 つ目の枠のせいで断られます
    - 掃除が `lowered` の lease を読むときは、セッションが `running` か `rescheduling` と読めるときだけ `user.interrupt` を送ります（ターンが自分で止め終えたセッションに、もう一度送らないため）。ほかの lease には、今までどおり、状態によらず送ります
    - 掃除が 1 回読んで lease を外した後に、初めて使用量が出た場合は、数えられません（「限界」）
  - 足した分は、台帳のファイルでは `limit_extra_cents` という別の項目に入ります。`/usage` に出る合計は、報告された額のままです
- 台帳を読めていない間、残ったセッションの片付けは、budget を下げるだけにします。額の記録、行の累積値の更新、渡した枠の返却（lease の解除）、delete / archive は、台帳を読めたプロセスが起動時に行います。読めないまま記録すると、額がそのプロセスのメモリにしか残らず、差分の基準だけが先に進むためです。下げ終えたセッションは覚えておき、同じプロセスが 60 秒ごとに interrupt を送り続けることはしません
- **回数の上限は作っていません。** ループが Anthropic 側にあり、bot は往復を数えて止められないためです。AGENTS.md の「呼び出し回数に上限」を、金額・時間・同時実行数で代えています（#76 の 3。本人の判断待ち）
- 時間は、同時実行の枠を得てから数えます。再開したターンは、最初に始めた時刻から数えます（本人の発言を送り直すことになった再開と、まだ送っていない発言を送ることになった再開は、新しく数えます）
- 利用額は `/usage`に、従来の推計とは別の行で出ます。セッションが額を報告しなかったターンは、合計に入れず、件数を別に出します（「額の報告が無かったターン: N（合計に入っていません）」）。この件数には、発言が取り上げられる前に終わったターンも入ります。判定では何も足さないターンなので、表示と判定で扱いが違います（表示を変えるかは、本人の判断待ち）。掃除や片付けが、額の無い使用量を記録したときも 1 増えるので、ターンの数とも一致しません（発言が取り上げられた後で `/clear` され、片付けが使用量を読んだ 1 ターンで、2 と出ます。`workspace-turn.test.ts`）

## 止め方と切り戻し

- **プリセットを非公開に戻しても、既に選んでいるサーバーは動き続けます。** 新しく選べなくなるだけです（設定の解決は、公開状態も鍵の有無も見ません）
- **鍵を外す**（`bot.env` から `ANTHROPIC_WORKSPACE_API_KEY` を消して再起動）: Workspace を選んでいるサーバーのターンは、すべて認証エラーになります。ほかのモデルには切り替わりません。片付け待ちのセッションの削除も、鍵が戻るまで進みません
- **サーバーごとにモデルを替える**（`/switch` かダッシュボード）: そのサーバーのセッションは archive されます
- 1 日の上限を最小（`ANTHROPIC_WORKSPACE_DAILY_BUDGET_USD=0.01`）にして再起動すると、残りが 5 セント未満になるので、新しいターンは「1 日の利用額の上限」の定型文で断られます。再開（`/retry`、起動時の自動の再開）も同じ残りで確かめるので、その再起動で中断したターンも、枠を残していれば断られます。コードの読み取りから言えることで、この値での動作そのものはテストしていません（残りを使い切った後の `/retry` が断られることは、`workspace-turn.test.ts` にあります）
- bot が壊れても効く歯止めとして、**Workspace 専用の Console workspace を作り、その spend limit を設定する**ことを勧めます（#76 の 8。本人の判断待ち）。Files API のファイルは同じ Console workspace のどの鍵からも読めるので、`anthropic` と鍵を分けるだけでは、ファイルは分かれません（公開文書の記述）

## 限界

- セッションの設定（プロンプト・ツール・web の有無）は作成時に固定され、配信では変わりません。変えるには、そのチャンネルのセッションを作り直す必要があります（会話と作業ファイルは失われます）
- コンテナの中身は作成から 30 日で失われます。会話は続きますが、ファイルは空になります
- 組み込みのシェル・ファイル・web のツールは Anthropic 側で動き、bot の権限チェックを通りません。確かめるのは、ターンの開始時、Hibana のツールが呼ばれたとき、イベントを読むたびです
- コンテナのネットワークは、既定で外に出られます（`ANTHROPIC_WORKSPACE_NETWORKING=unrestricted`。#76 の 7、本人の判断待ち）。読んだ内容に動かされて、コンテナの中身を外へ送る危険は、公開文書が挙げています。`limited` にすると、`ANTHROPIC_WORKSPACE_ALLOWED_HOSTS` のホストとパッケージの配布元だけになり、web 検索と web 取得も同じ一覧で絞られます。Discord の CDN を一覧に入れないと、添付を取得できません
- SDK は環境変数 `ANTHROPIC_CUSTOM_HEADERS` を読み、その内容をリクエストのヘッダーに足します。bot の環境にこの変数があると、Workspace のリクエストにも付きます。ただし、**鍵（`x-api-key`）と `Authorization` は置き換わりません**。認証以外のヘッダーは、そのまま付きます（落とさないのは AI の案、本人未確認。代案は「この変数があれば Workspace のターンを認証エラーで止める」「全部落とす」）
  - 固定するのは、SDK に渡す `fetch` の中です。送信の直前に、`x-api-key` を Workspace の鍵に設定し、`Authorization` を消します。SDK がヘッダーを重ねる順序には依りません。SDK はこの変数の行を、オブジェクトのキーとして認証のヘッダーの上に重ねるので、同じ名前を綴り違いで 2 回書くと（`X-Api-Key`、次に `x-api-key`）、クライアントに値を渡すだけでは、後に書いた綴りが残って送られるためです。同じ名前を綴り違いで何回書いても、置き換わりません。イベントのストリームと、ファイルの一覧・取得も、同じ `fetch` を通ります
  - クライアントに渡す値（鍵と、`Authorization` を送らない指定）も残しています。SDK は、認証のヘッダーが 1 つも無いリクエストを、送る前に自分で断ります。`x-api-key:`（値なし）の行で鍵が空になったときに、その検査を通すためです（2 段にしたのは AI の案、本人未確認。代案は `fetch` の中だけにすることで、その場合は、値なしの行がある環境で送信前のエラーになります）
  - 根拠は、SDK 0.133.0 のコードの読み取りと、偽の `fetch` でのテストです（`workspace-client.test.ts`。セッションの読み取り、イベントの送信、ストリーム、ファイルの一覧と取得）。実 API には送っていません
  - 本番の bot は、クライアントに `fetch` を渡しません（グローバルの `fetch` を包んで使います）。この経路は、偽の `fetch` を渡すテストでは通らないので、1 件だけ、`fetch` を渡さずに 127.0.0.1 に立てたサーバーへ送るテストで確かめています（セッションの読み取り、イベントの送信、ストリーム、ファイルの取得の 4 リクエスト。送る前に、クライアントの接続先がそのサーバーと完全に一致することを確かめ、違えば何も送らずに失敗します）。逆に、`fetch` を渡したクライアントが、グローバルの `fetch` を 1 回も呼ばないことも、同じ 4 リクエストで確かめています
  - 送信前のエラーになる書き方が、確かめた範囲で 1 つ残っています。両方のヘッダーを「正規の綴りが先、別の綴りが値なし」で書いた場合です（`X-Api-Key: …`、`x-api-key:`、`Authorization: …`、`authorization:` の 4 行。片方のヘッダーだけなら送れます）。リクエストは 1 件も出ず、鍵も出ませんが、Workspace のリクエストはすべて失敗します。SDK のエラーではない素の例外なので、プロバイダーの失敗としては分類されません（偽の `fetch` で確かめました。`fetch` を包む前の版でも同じ結果です。リポジトリの自動テストにはありません）
- 鍵・`authToken`・接続先は必ず明示して渡すので、`ANTHROPIC_API_KEY`・`ANTHROPIC_AUTH_TOKEN`・`ANTHROPIC_BASE_URL` は使われません
- 同じチャンネルで、個人のモデル設定が違う人が交互に話すと、そのたびにセッションを作り直します（会話のキーが人ごとに変わるため）
- archive したセッション、定義を変える前のエージェントと environment は消しません。Anthropic 側に溜まります
- セッションを作るリクエストの結果が分からないまま失敗すると、どの表にも無い idle のセッションが 1 つ残ることがあります。それを探して消す処理は入れていません
- 片付け待ちに入った archive は、後から同じチャンネルを `/clear` しても delete に変わりません
- **workflow run が開いたままのセッションは、delete / archive が 400（`workflow_run_open`）で拒否されることがあります**（公開文書の記述。「成功することもある」とも書かれています。実 API でどうなるかは未確認です）。止まった run は、寿命（既定 24 時間）が過ぎるまで自分では終わりません。実装は、上限や追加発言で止めた run を開いたまま残すので、Haiku Ultra のチャンネルでは、`/clear` やモデルの変更の後も、その間は会話と作業ファイルが Anthropic 側に残りえます（`/clear` の返信は「削除を始めました」です）。片付けは 60 秒ごとに 5 回まで試し、その後は次の bot の起動まで試しません。拒否の理由を見分けて待ち続ける処理も、先に run を止める処理も入れていません（#76 の 6 とあわせて、本人の判断待ち）
- bot がサーバーから外されても（kick）、そのサーバーのセッションは止めも片付けもしません。実行中のターンは 1 ターンの上限（金額・時間）まで続き、行と、Anthropic 側の会話・作業ファイルは残ります。ほかのプロバイダーのターンも、外された後に会話履歴やサンドボックスの作業領域を片付けていないので、それに合わせています（片付けるか、片付けるなら archive か delete かは、本人の判断待ち）
- 同じチャンネルで順番を待っている発言には、待っていることの表示が出ません。`/clear` は、待っている発言を消しません
- budget で止まった後の次の発言では、budget を上げた時点で前の作業が再開し、発言と一緒に送る interrupt が届くまで進みます。その分はこのターンの枠から出て、前の作業が出したものは捨てます。前の作業が枠を使い切ると、発言は取り上げられないまま、ターンが budget の定型文で終わり、発言はセッションのキューに残ります。budget を上げてから発言を送るまでの間に新しい上限に達した場合は、発言の送信が 400 で断られ、ターンは失敗になります（budget の定型文にはなりません）
- ストリームを開き直したときに、自分の発言が一覧に処理済みとして無ければ、その間のイベントは再生しません（前のターンを再生しないための安全側）。`processed_at` が処理の終わりに付く API だった場合、休んでいた（idle の）セッションへのターンは、動いている間ずっと、自分の発言を処理済みとして見つけられません。開き直すたびに何も再生しないので、接続が切れていた間の Hibana のツール呼び出しには答えられず、ターンは時間の上限まで待ちます（偽のセッションで再現しました。リポジトリの自動テストにはありません。「検証していない範囲」）。**実 API では、取り上げの時点に付きました**（2026-10-12 の 2 回の実行で、エージェントの最初のイベントと同じ時刻。Haiku 5.5 の Ultra なしのセッション）。その実行では、この形は起きていません。ターンの途中でストリームを開き直す項目（smoke の「a stream opened again in the middle of a turn」）も通りました
- **ストリームを開き直した直後に、前の作業の最後の文を返信にして、ターンを終えてしまう場合があります。** 次の 4 つが重なったときです（偽のセッションで再現しました。リポジトリの自動テストにはありません）
  1. 前の作業が残っていたセッションへのターンである（「どこからがこのターンか」の「それ以外」の側。追加発言の後でまだ止まり切っていない、budget で止まった後、run が開いている、取り上げ前の発言が残っている、など）
  2. 発言を送ってから取り上げられるまでの間に、ストリームが切れる
  3. 開き直した接続が開いた後、一覧を読むまでの間に、前の作業が終わって、発言が取り上げられる（一覧が発言の位置を決め、前の作業の最後のイベントは、新しい接続に届きます）
  4. 前の作業の最後のイベント（文と、`end_turn` の idle）の `processed_at` が、発言の `processed_at` と同じ時刻である（秒までの精度だと、普通に並びえます。公開文書の例は、どれも秒までの精度です）

  このとき、時刻の比較（「より前」だけを前の作業にする）では分けられず、前の作業の最後の文が返信になり、ターンはすぐに終わります。終わるときに budget を「消費済み + 1 セント」に下げるので、発言を取り上げて動き始めた本物のターンも止まります。比較の向きを変えても直りません（同じ時刻のものを前の作業にすると、取り上げと同じ時刻に出た、このターンの呼び出しを断ることになります）。時刻ではなく一覧の順序で分ける案がありますが、実 API の時刻の精度と、一覧が同じ時刻のイベントを起きた順に返すかを smoke（「the event list, newest first」）で見てから、直し方を決めます

- 400 で断られたツールの結果は、公開文書の手順（スレッドの状態を確かめる）を踏まずに、定型の error の結果を 1 回試して、それも断られたら捨てます。遅すぎた結果と、内容が受け取られなかった結果を、bot は見分けません
- 1 日と月の判定は、多めに数える側に倒しています（新しいセッションごとに 1 セント、使用量の報告があるのに額の報告が無い区間は枠の全額、チェックポイントだけが覚えていたセッションは累計の全額）。実際より早く上限に達して、ターンを断ることがあります。チェックポイントだけが覚えていたセッションの額は、今のターンのモデルの行に足すので、モデル別の内訳は実際と違いえます
  - 少なく数える側の穴は、次の 4 つです。どの場合も、1 ターンの上限（session budget）は Anthropic 側で効きます
    - 使用量の報告がまったく無い区間は、何も使っていないものとして扱います（「上限と費用」）。作業したのに、額もトークンも稼働秒数も報告しないセッションがあると、判定に入るのは、セッションを作ったときの 1 セントだけです。そういうセッションが実 API にあるかは確かめていません
    - 使用量も額も見えないまま終わったターンの枠を数えられるのは、次の掃除か、その前の片付けが読むときまでです。掃除が 1 回読んで何も無く、lease を外した後に、初めて使用量（額なし）が出ると、その使用量は枠なしで記録され、判定には入りません。そのセッションへの次の発言は、「使用済みなのに額が無い」（`list_cost_missing`）で失敗します（偽のセッションで見ました。リポジトリの自動テストにはありません）。`/clear` の片付けは、ターンの最後のリクエストの直後に読むので、数えられるのは、その短い間に出た使用量だけです。その後に出た分は、セッションが削除されているので、記録もされません（額を報告するセッションの実額も同じです）
    - 同じセッションで次のターンが新しい枠を付けると、前のターンの、まだ数えていない枠（`lowered` の lease）は捨てます。数えるのは、最後の lease の枠だけです。budget は累計の上限なので、最後に置いた上限を超えては使えない、という考えによります（コードの読み取りによる。AI の案、本人未確認）

  - 最初は額を報告せず、後から額を報告するようになったセッションでは、数えた枠と、報告された額の両方が判定に入ります（コードの読み取りによる。断る側に倒れます）

- **run が開いたままターンが終わるとき、同じ文が、進捗と返信の 2 回、チャンネルに出ます。** run が開いている間にモデルが止まるときに書いた文は、その場で進捗に出します（「Haiku Ultra」）。run が止まったまま残ってターンが終わると、その同じ文が返信の本文にもなるためです。偽の API では、「ワークフロー: …」（run の状態）、「調査を始めました。」（進捗）、「調査を始めました。」に run が残っている旨の定型文を足した返信、の順に出ました。run が動き続けて終わる通常の流れでは、重なりません（進捗に出すのは AI の案、本人未確認。代案は「セッションが running に戻った時点で進捗に出す」）
- 「前のターンの run が開いている」という注記は、前のターンの記録から作るので、既に終わった run を挙げることがあります
- 起動時の片付けは 1 セッションにつき 30 秒までで、片付け待ちが多いと Workspace のターンの再開が遅れます
- ダッシュボードの「実際の動作」は bot の環境変数を知らないので、`WORKFLOWS_ENABLED=false` などで Haiku Ultra が働いていなくても `ultra` と出ます。マイ設定の要約はモデル名だけなので、Anthropic と Anthropic Workspace の区別が付きません

## 実 API での確認

**2026-10-12 に、持ち主の承認のもとで AI が実行しました**（#76 の 11）。smoke スクリプト（`apps/bot/src/workspace/smoke.ts`）を、Haiku 5.5・effort medium で流しています。Haiku Ultra は、bot 自身のターンの区間の 1 ターン（`--bot-only --ultra`）だけを流しました。スクリプト側の Ultra の区間（`--ultra`）は流していません。上限（合計 $1）と鍵（`ANTHROPIC_API_KEY` の値を、その実行のプロセスにだけ渡す）は、持ち主が選びました。結果は、この節の最後の「2026-10-12 の実行」にあります。課金されるので、次に流すときも、そのつど持ち主の承認が要ります。

```sh
cd apps/bot
bun run workspace-smoke                # Haiku 5.5、plain のセッション 1 つ
bun run workspace-smoke --ultra        # 加えて Haiku Ultra のセッション（workflow run）
bun run workspace-smoke --bot          # 加えて bot 自身のターン（ツールは bot の registry が実行する。Discord は偽）
bun run workspace-smoke --bot-only     # bot 自身のターンだけ（--ultra を付けると、最後に Haiku Ultra のターンを 1 回）
bun run workspace-smoke --budget 0.5   # セッションごとの budget（USD。0.2〜10、既定 1）
bun run workspace-smoke --keep         # 作ったものを残す（budget は下げる）
bun run workspace-smoke --cleanup      # 以前の実行が残したものを消すだけ
```

- `ANTHROPIC_WORKSPACE_API_KEY` が要ります。課金されるのは、モデルのトークン、セッションが動いていた時間、web 検索です。`--budget` はセッションごとの上限なので、`--ultra` を付けると 2 セッションぶんになります。`--bot` の区間は、bot 自身の上限で止めます（1 日と月の上限を `--budget` に、1 ターンの上限を 20 セント、Haiku Ultra のターンの上限を 40 セントにした設定で bot を組み立てます）。これも `--budget` ぶんなので、3 つの区間を全部流すと、最大で `--budget` の 3 倍です。ほかに、発言を送らない budget 1 セントのセッションを 3 つ作ります（effort の `xhigh`・`max` が受け付けられるかの確認と、archive を 2 回送る確認）。全体は 15 分で打ち切ります
- **`--budget` を超えて budget を引き上げません。** 各ターンの前にセッションを読み、実際に使われた額を合わせてから、そのターンの枠を「`--budget` の残り」以下にします（途中のステップが失敗しても、手元の額がずれないようにするため）。読んだ後に額が増えていて、引き上げ先が `--budget` を超えるステップは、budget を上げる前に失敗にします（わずかに超えてでも観測する、という選び方もあります。AI の案、本人未確認）
- environment・エージェント・セッションは、bot と同じ `WorkspaceResources` で作ります（名前で探す → 無ければ作る → セッションを作る → 作ったセッションを検査する）。bot の最初のターンが通る作成の経路を、そのまま実 API に当てるためです。名前は実行ごとの `hibana-smoke-<実行ごとの文字列>-…`、`metadata.app` は `hibana-smoke` で、データディレクトリは一時的なものです。bot のもの（名前が `hibana-workspace-…`、`metadata.app` が `hibana`）は採用しません。名前が同じでも、`metadata.app` が違うものは採用しません（`workspace-resources.test.ts`）
- 後片付けは、セッションを止めて budget を下げてから delete し、environment とエージェントは 1 つずつ読んで、`metadata.app` が `hibana-smoke` であることを確かめてから消します。**途中で落ちたら `--cleanup` を実行**してください（`metadata.app` で探します）
  - セッションの delete が失敗したら、5 秒おきに 6 回まで試します。それでも消せなければ `NOT deleted` と出して、cleanup を FAIL にします
  - archive 済み・terminated のセッションで、delete を**断られた**ものは、試し直さずに残します（`left archived or terminated`）。「断られた」は、応答があって、やり直しても変わらない status のことです（408・429・5xx と、応答なしは含めません。404 は「既に無い」として扱います。線引きは bot の `httpFailure` と同じです）
  - 残したセッションが参照している environment も、delete を断られたら残します（`environment … left: N session(s) that were left still refer to it`）。公開文書は、environment を消せるのを「参照するセッションが無いとき」としているためです。この 2 つは **cleanup を FAIL にしません**。行と、最後の要約に出るだけなので、終了コードだけを見ていると気づけません（AI の案、本人未確認。代案は「FAIL のまま、`--cleanup` の案内だけ外す」）。残ったセッションが参照していない environment の失敗と、5xx・応答なしでの失敗は、今までどおり FAIL です
  - 「run again with --cleanup」と出るのは、やり直して直りうる失敗があるときだけです。`metadata.app` の付いていない資源は、消さずに FAIL にしますが、この案内は付きません（`--cleanup` でも消さないため）
  - スクリプトには、残したセッションと environment を消す手段がありません。実 API が archive 済みのセッションの delete を断る場合、smoke を実行するたびに、セッション 1 つと environment 1 つが残ります（「archiving a session twice」の確認が、毎回 archive 済みのセッションを 1 つ作るため）。**2026-10-12 の実行では、archive 済みのセッションの delete は受け付けられ、何も残りませんでした。** environment の delete を断るときの status、Console などから消せるかは、確かめていません（公開文書が、delete を断る、または断ることがあると書いているのは、`running` のセッションと、workflow run が開いているセッションです。archive 済みのセッションの delete についての記述は見つけていません）
  - 後片付けのこれらの確認は、スクリプトの写しを偽のサーバーに向けて確かめただけで、リポジトリの自動テストにはありません。`--cleanup` のやり直しも、別のプロセスではなく、同じプロセスの中で模したものです
- plain と `--ultra` の区間では、Hibana のツールは実行せず、結果はスクリプトが与えます。発言の本文とエラーの本文は出力しません（エラーは、status・コードと、メッセージが触れているフィールド名だけを出します）
- `--bot` の区間は、bot（`Hibana`）を 1 つ組み立てて、発言を `Hibana.respond` に渡します。セッションの表、上限、プロンプト、ツール一覧、custom tool の実行（`ToolRegistry` の引数の検査と権限の確認）を、bot のコードのまま実 API に当てるためです
  - **Discord には接続しません。** Discord のクライアントはログインせず、チャンネルとサーバーの問い合わせにはスクリプトが決めた内容を返し、REST の呼び出しは送らずに記録します。記録を見て、ツールが何をしたかを判定します。その区間の間は、API のクライアント以外からの通信（グローバルの `fetch`）を断り、断った宛先のホストを数えて出します
  - bot の設定は、デプロイのものではなく、最小のものです。Jev・公開サイト・スキル・sandbox は無効で、セッションの作り方を決めるもの（`ANTHROPIC_WORKSPACE_*`、`WEB_SEARCH_ENABLED`、`PERSONA_FILE`）だけを引き継ぎます。その設定でのツールは 72 個です（plain の区間は、全部を有効にした 76 個で作ります）
  - 作るものの名前とラベルは、ほかの区間と同じ `hibana-smoke-…` です。bot に名前とラベルを渡す口（`WorkspaceDeps.identity`）は、このスクリプトとテストだけが使います（`workspace-turn.test.ts`）
  - registry が断ったツール呼び出しは、bot 自身の理由の文を出します（「You cannot read this channel」など）
  - `--ultra` を付けると、この区間の最後に Haiku Ultra のターンを 1 回流します（`--bot-only --ultra` なら、bot のターンだけで、スクリプト側の Ultra の区間は流しません）。Ultra は、ダッシュボードと同じ経路（`runtime.patch`）で保存します。次の発言は新しい会話になり、ultra の variant のセッションで始まります。workflow run のエージェント 2 つに、`read_messages` と `send_message` を 1 回ずつ呼ばせます。run のエージェントからの呼び出しは、registry が worker として実行するので、読むほうは実行され、投稿するほうは断られます
- 確かめる項目:
  - 作成: environment とエージェント、76 個のツール定義つきのセッション、同じ名前のエージェントをもう 1 つ作れるか、保存したファイルを消した後に名前から採用できるか、effort の `xhigh`・`max`、同じセッションを 2 回 archive したときの応答
  - 1 ターン: 応答、最初の発言を送った直後のセッションの読み（下の「最初の発言の直後の観測」。判定なし）、発言が処理済みになる時点（ターンの始まりか終わりか）、送ったばかりの発言が、発言の一覧（新しい順）の先頭に、送信が返した id で載っているか、ストリームが発言を処理済みとして届けるか、usage の報告、添付画像、組み込みツール、custom tool の往復
  - ファイル: outputs のファイルが Files API に出ること、サブディレクトリのファイルの `filename` の形（「listed under …」と出ます。照合できなかったときは、その名前で載っているファイル名を 3 件まで出します）、同名の上書き
  - 続き: 2 ターン目が同じセッションで続くこと、ターンの途中でストリームを開き直すこと（無音の上限を 6 秒にして、20 秒かかるコマンドを実行させます。コマンドの出力が返信に 1 回だけ出ることを見ます）、イベントの一覧の並び、idle のセッションへの interrupt、実行中の interrupt
  - budget: budget での停止、消費済み以下の budget への更新が断られる形、budget で止まった後のターン（budget を上げた後に前の作業が進んだか、そのとき送った発言が一覧のどこに載り、ストリームにどう届いたかも出します）
  - `--bot`: bot 自身のターンの返信、bot が作ったセッション（モデル、effort が medium、ツールの数、ラベル）、読むだけのツール 2 つ（`read_messages`・`get_bot_settings`）、変更するツール 2 つを順に（`send_message` の後に `add_reaction`。メンションが無効で送られること）、コンテナのファイルを `send_file` で渡すこと（Files API から取り出したバイト列が、書いたものと同じこと）、本人が読めないチャンネルへの `read_messages` が断られ、Discord には問い合わせず、失敗の結果として API に受け付けられること、コンテナのファイルのツールと `web_fetch`（bot には来ないこと）、bot の台帳が持つ額がセッションの報告以上であること、Messages API のクライアントを使わないこと、`/clear` でセッションが削除されること
  - `--bot` と `--ultra`: 保存した Ultra で ultra の variant のセッションが作られること（workflows が有効なエージェント）、workflow run が始まって終わり、開いたまま残らないこと、run のエージェントからの `read_messages` が worker として実行され、返信にその内容が出ること、run のエージェントからの `send_message` が断られ、Discord には何も投稿されないこと、bot の台帳が持つ額がセッションの報告以上であること
  - `--ultra`: Haiku 5.5 で workflows を有効にしたエージェントが作れること、workflow run の開始から終了まで、run の中からの custom tool の呼び出し、budget で止めて interrupt した run が、budget を上げても止まったままか、開いた run を発言で止められるか
- **最初の発言の直後の観測**（判定なし。PASS / FAIL の数にも、終了コードにも入りません）。plain のセッションの最初のターン（「reply」）で、発言を送った直後に、セッションを 1 回読み（1 回の実行で GET が 1 件増えます）、続けて、前からある発言の一覧の読み取りを行って、結果を 1 行の INFO にします。行は、ターンの途中（`PASS reply` より前）に出ます。その後でターンが失敗しても出ます

  ```
  INFO  the session right after its first message was sent: idle, no list cost, 0 active seconds, 0 input tokens, 0 read from cache, 0 written to cache, 0 output tokens; the message was then entry 1 of 1 in the list of messages, still queued
  ```

  - 見たいのは、実装が置いている前提です（「検証していない範囲」）。新しいセッションは、最初の発言が取り上げられるまで、`usage` に何も（額もトークンも稼働秒数も）報告しないこと。取り上げ前の発言が、発言の一覧に `processed_at` なしで載ること。行の先頭の status は、取り上げ前の発言が残っているセッションの `status` の観測です
  - セッションを一覧より先に読みます。一覧が「still queued」なら、セッションを読んだ時点でも、発言は取り上げ前でした
  - 読み方（左が出力、右が、その形のときに言えること）

    | 出力                                                                                                                 | 言えること                                                                                                                                                                 |
    | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | `no list cost`、数字がすべて 0、`still queued`                                                                       | 前提どおり                                                                                                                                                                 |
    | `a list cost of 0 cents`（または別の額）、`still queued`                                                             | 取り上げ前から額を報告する API。「使用済みなのに額が無い」の判定も、取り上げ前の発言を調べる処理も、通らない                                                               |
    | `no list cost` で、active seconds かトークンが 1 以上、`still queued`                                                | 取り上げ前から使用量だけを報告する API。同じ人が言い直した 2 つ目のターンは `list_cost_missing` で失敗する                                                                 |
    | `not among the N message(s) listed, by the id the send returned`                                                     | 送った発言が、一覧（新しい順の最初のページ）に載っていない。取り上げ前のイベントを一覧に載せない API なら、残っている発言が分からず、idle のセッションとして送ることになる |
    | `already processed (so the session may have been read after it was taken up)`                                        | 読むのが間に合わなかった。前提については何も言えない                                                                                                                       |
    | `a list cost the bot cannot read`                                                                                    | `list_cost` はあるが、bot が額として読めない形（USD の整数セントの文字列でない）                                                                                           |
    | `the session could not be read`、`the list of messages could not be read`、`the send returned no id for the message` | その読み取りができなかった（ターンは続く）                                                                                                                                 |
