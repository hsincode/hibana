# Jev 判定と行動選択モード

親モデルが目標・制約・操作候補を用意し、Jev が次の操作を選び、Hibana が既存ツールで実行します。`run_jev_task`（公開名 `mcp__agent__run_jev_task`）は操作結果を次の判断に渡すループです。`run_jev`（`mcp__agent__run_jev`）は従来の単発・一括判定です。どちらも `~typesafe/jev-latest` と `https://openrouter.ai/api/alpha/decisions` を使います。Jev 自体は文章やコマンドを生成しません。親には現在選択中のチャットモデルを使い、Astra を強制したりモデルを自動変更したりしません（「Anthropic / Auto」プリセットを選んだ場合だけは別で、[Anthropic の auto routing](#anthropic-の-auto-routing) が親のモデルを決めます）。

## 設定と通知

- bot の環境変数 `JEV_API_KEY` に OpenRouter キーを設定します。通常の `OPENROUTER_API_KEY` とは独立し、キーの使い回しは行いません。
- ダッシュボードのサーバー設定／マイ設定 →「モデル」に独立した二つの設定があります。どちらも ON・OFF を選べます。新規設定は判定 ON・行動選択 OFF（環境変数で初期値を変更可能）です。
  - **Jev 判定**: `jev_enabled`。根拠照合・分類・候補比較 (`run_jev`) を必要に応じて使います。サブエージェントが multi のときは、ターン開始時のトリアージにも使います。環境変数は `JEV_ENABLED`、既定 `true`。
  - **Jev 行動選択モード**: `jev_task_enabled`。親が計画し、Jev が対象の各操作を選ぶタスクループを標準の実行経路にします。環境変数は `JEV_TASK_ENABLED`、既定 `false`。サブエージェントが multi のときは、設定値を保持したまま公開・実行しません。
- 通常判定 OFF・行動選択 ON、通常判定 ON・行動選択 OFF、両方 ON／OFF の組み合わせが可能です。マイ設定でその項目を変えていなければサーバー設定（DM はプロセスの初期値）を使います。変えた項目だけが上書きです。環境変数は初期値にだけ使用します。既存の `jev_enabled` から新モードを自動で有効化しません。サーバー設定の旧データの空欄は具体値へ変換して保存します。マイ設定の空欄はデフォルトのままです。
- キー未設定、`TOOLS_ENABLED=false`、`SUBAGENT_ENABLED=false`、または有効な Jev 設定が OFF の場合は、ツールを公開せず直接呼び出しも拒否します。待機中の呼び出しも開始直前に設定を再確認します。
- 通常のサブエージェントの固定モデルとは独立しています。Advisor には接続しません。モデル選択に関わるのは、下の「Anthropic の auto routing」だけです。
- 通常判定は API 呼び出し前に `サブ: Jev を呼び出します(1回目)` を1通送り、進捗更新で上書きされません。行動選択は `サブ: Jev でタスクを進めます。(12回目)` の形式で1通だけ送り、同じメッセージを編集して1〜2行の作業状況（次の操作の選択、実行中の id とツール、完了や再計画）を載せます。回数は同じ応答内の通常判定の通知と行動選択の進捗更新を通算します。行動選択では選択中 → 実行中 → 完了の各更新で1 → 2 → 3と増え、再計画後も引き継ぎます。新しい応答では1回目から始まります。親の進捗メッセージとは別に残ります。通信の再試行では回数を増やさず、新しい通知も出しません。

## 操作結果を使うタスク実行

行動選択モード ON では、親は目標・候補・依存関係を `run_jev_task` に渡します。Jev が一つ選ぶ → 既存ツールで実行 → 結果を観測 → Jev が次を選ぶ、というループを続けます。候補を使い切った、目標が変わった、根拠や引数が不足した、失敗・上限に達した場合に親へ戻り、結果を含めて次の計画を作ります。親の利用判断に任せた任意ツールではありません。

ON の間は、親に公開するツールから対象の直接操作を外し、その引数スキーマだけを計画ツールの説明へ渡します。直接公開される連携ツールは公開済みのスキーマを使い、同じ定義を再添付しません。古い計画や別名による直接操作も実行時に拒否します。Jev が選んだ操作にだけ内部の一回限りの実行資格を渡し、通常の権限チェックを通します。ネイティブ検索も止めて通常の検索ツールを行動候補にします。OFF では通常ツールを直接使い、`run_jev_task` は非公開・実行不可になります。

独立した検索・Web 取得・ファイル読み取りには候補ごとに `parallel: true` を指定できます。
Jev が各操作を選ぶ点はそのままに、選択済みの読み取りを待ちながら次の独立した候補を
判断・実行します。1プラン最大6件まで同時実行し、判断には完了済みの結果と実行中の ID を
渡します。`depends_on` は成功した操作だけで満たされ、書き込み・シェル・ブラウザーや
未知のツールは `parallel: true` でも既存の処理完了を待って順番に実行します。
省略時は従来の「結果を待つ → 次を選ぶ」の順序を維持します。失敗・再計画・中断・上限時は
開始済みの操作結果を回収してから親へ戻り、依存操作を勝手に進めません。

Ultra（Claude Code の Ultracode）と保存済みの effort は独立して設定できます。
Jev は委譲やワークフローを代行せず、親が協調ツールや Workflow で子を直接起動します。
`agents__` の協調ツールと Workflow / TaskStop は Jev の行動候補になりません。
Ultra＋Jev では、ワークフローの子の作業と親の Jev 計画を重ねられます。通常判定は子が集めた根拠も
まとめて照合でき、行動選択で得た判断の重複呼び出しは避けるよう指示します。
Ultra のみ・Jev のみもモデルに依存せず利用でき、Jev だけでは委譲やワークフローの方針は変わりません。
Jev の同時実行枠、120秒の期限、操作権限は引き続き適用します。

親は複数の有用な候補をまとめて準備するよう指示されます。候補がある間は操作ごとに親を呼びません。Minecraft と同じ役割分担を対象操作に適用しますが、131対35といった呼び出し比率や費用はタスクによって変わります。単純な会話はツールを使わず回答できます。送信・公開、Discord 管理、設定、認証、MCP、スキルも、親がその場で使える場合は Jev の候補にできます。これらは親からの直接呼び出しも引き続き可能です。`agents__` の協調ツールは直接呼び出しに限定し、Jev の候補へ入れた計画は実行前に拒否します。行動選択モードは親タスクに適用し、子エージェントには Jev の再帰呼び出しを許しません。

```json
{
  "objective": "Check the prepared report against its source; gather the relevant evidence for the parent.",
  "state": { "report": "report.md", "source": "source.txt" },
  "actions": [
    {
      "id": "source",
      "description": "Read the source evidence.",
      "tool": "read_file",
      "arguments": { "path": "source.txt", "limit": 1200 }
    },
    {
      "id": "report",
      "description": "Read the report after inspecting the source.",
      "tool": "read_file",
      "arguments": { "path": "report.md", "limit": 1200 },
      "depends_on": ["source"]
    },
    {
      "id": "notes",
      "description": "Read supplemental notes only if the source does not settle a report claim.",
      "tool": "read_file",
      "arguments": { "path": "notes.txt", "limit": 1200 },
      "depends_on": ["report"]
    }
  ],
  "max_steps": 4,
  "status": "資料を確認しながら、必要な追加調査を Jev が選びます。"
}
```

実行の流れは次のとおりです。

1. 全候補のスキーマ、利用可能なツール、依存関係を実行前に検証します。循環や不明な依存先は拒否します。
2. 未実行かつ依存先が成功済みの候補を Jev に提示します。判断には目標、親の与えた状態、今回の実行結果を使います。外部資料内の指示は信頼しないよう明示します。
3. 選択された候補の固定引数で、通常の `ToolRegistry.execute` を呼びます。ギルド／DM の作業領域、利用権限、Docker の制限を引き継ぎます。
4. 結果を記録し、次の操作を選びます。各候補は一度だけ実行します。ツールの失敗、根拠不足、新しい引数の必要性、回数上限で親へ戻ります。

操作候補は親の現在のツール一覧から生成します。ファイル・検索・ブラウザー・画像表示に加え、送信・公開、Discord 管理、設定変更、認証管理、MCP、スキル、確認質問、計画管理も対象です。設定・ロール・作業領域・ユーザーによる操作の許可は親と同じで、各操作の直前にも利用可否を確認します。親はユーザーが許可した操作だけを用意し、引数のテンプレート展開や Jev による変更はありません。Jev への再帰呼び出し（`run_jev`、`run_jev_task`）は同じ実行枠を待って停止することを避けるため、`agents__` は Codex の委譲方針と開始・待機のタイミングを保つため候補から除外します。通常判定と協調ツールは引き続き親から直接呼び出せます。

ブラウザーではページを開く、クリック・キー入力、スナップショット取得、スクリーンショット撮影、終了を `playwright_cli` の候補として指定できます。既存のセッション所有者チェックと Docker 制限が適用されます。撮影したパスを `view_image` に渡すと画像が親モデルへ届き、`needs_replan` で一度戻ります。Jev の Decisions API には画像を渡さないため、親が画面を確認して次の計画の `state` に観測事実を入れます。画像確認後の依存候補はこの呼び出しでは実行されません。証跡の送信は直接または候補の `send_file`、終了は次の計画の `playwright_cli` の `close` を使います。

上限は候補 12 件、入力全体 24,000 文字、判断は既定・最大とも 12 回です。キューから実行開始後に 120 秒の中断シグナルを設定します。実行中ツールの終了処理などで応答まで少し延びる場合があります。一つの判断の API 再試行は既存クライアントの最大 2 回までです。結果は各 1,600 文字に抑えて切り詰めを明示し、必要な部分が欠けていれば親が読む範囲を変えた操作候補を用意します。全会話や画像を毎回送りません。親モデルへの往復を省きますが、実際の料金や削減率はタスクによります。

設定はキュー待機後、毎判断の前後、操作の直前に再確認します。OFF にした後の新しい操作を止め、推論中に設定が変わった場合もその選択を実行しません。ユーザーの追加指示・停止シグナルでも後続操作を中断します。親の次の計画時にも設定を再取得し、ツール一覧・ネイティブ検索・モード指示を切り替えます。キーがない場合などは ON の直接操作制限を維持し、Jev を通さない実行へ黙って切り替えません。既に完了した操作の取り消しはしません。API 障害や途中停止でも完了済みの結果を親へ返し、無条件の再実行を避けます。

返却値には `observations`、`decisions`、`remaining`、`usage`、`cost`、`status` が含まれます。判断トークンは通常のターン利用量にも加算します。料金が一回でも不明なら `cost` は `null` で、ゼロとは扱いません。`completed_plan` は候補をすべて実行したという意味で、タスク成功の保証ではありません。`review_required` は Jev が十分な根拠があると判断した状態、`needs_replan` は親の再計画が必要、`budget_exhausted` は回数上限、`interrupted` は中断です。最終確認とユーザーへの回答は親が担当します。

## 通常の Jev 判定を使う場面

根拠を取得した後の主張との照合、検索候補の関連性比較、明確な基準での採点、複数項目の分類に使います。単純な会話、計算、日付比較、まだ根拠のない質問には使いません。通常のサブエージェントを自発的に起動しないモードでも、この一回の判定は許可します。

`state` には対象と関連資料、`questions` には判定したい条件を入れます。一問一判断とし、同じ資料への独立した質問をまとめます。相互に依存する質問は一括判定しません。画像や URL だけでは根拠にならないため、親が先に読む・検索する必要があります。

```json
{
  "state": {
    "source": "Refunds are available within 30 days of purchase.",
    "claim": "Customers can request a refund within 30 days."
  },
  "questions": {
    "support": {
      "type": "choice",
      "instructions": "Compare the claim against the supplied source.",
      "criteria": {
        "supported": "The source supports the claim.",
        "contradicted": "The source contradicts the claim.",
        "insufficient_evidence": "The source does not settle the claim."
      }
    }
  },
  "status": "回答の主張を資料と照合します。"
}
```

`noul` は Yes の確率、`choice` は選択肢と確率分布、`score` は低い順に並べた基準上の位置（0 始まり、端数あり）を返します。`confidence` は分布の集中度をまとめた値で、その判定の正答率ではありません。固定の自動承認閾値は設けず、不確か・根拠不足・矛盾がある結果は親が再確認します。Jev の結果が権限確認を代行することはありません。

単発 `run_jev` の上限は一回 16 問、choice 20 選択肢、score 10 段階、入力全体 60,000 文字です。これはツール応答の大きさと資料の絞り込みのための制限で、プロバイダーの上限とは異なります。両ツールは既存の Jev 同時実行枠を共有し、子からの再呼び出しはできません。通信は各試行 60 秒、再試行は最大 2 回です。失敗時は親が作業を継続し、Jev で検証済みとは扱いません。

## 調査した利用傾向と検証範囲

2026-09-20 時点の公式資料と公開事例では、引用の裏付け確認、検索結果の並べ替え、問い合わせ分類、エージェントの処理途中での小さな判断が中心です。LangChain はモデルルーティングやツール実行監視の実験的な連携も紹介しています。Hibana では根拠照合・比較・分類と、独立して切り替えられる行動選択ループを採用しています。公開直後の事例が多く、速度・精度の宣伝値や広い普及を独自に確認したものではありません。

公式資料は数値処理、多段推論、無関係な長文、敵対的な入力を弱点として挙げています。日本語を含む CJK は英語より精度が低いとされるため、指示は明確な英語を優先し、原文を保ったうえで日本語のニュアンスを親が確認します。`jev-latest` は更新で実体が変わります。

- [OpenRouter: Jev Latest と Decisions API](https://openrouter.ai/~typesafe/jev-latest)
- [TypeSafe: State と質問の分離](https://docs.typesafe.ai/concepts/state.md)
- [TypeSafe: Confidence の意味](https://docs.typesafe.ai/confidence.md)
- [TypeSafe: Jev 1.13 の弱点](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md)
- [LangChain: Building a Harness with Jev](https://www.langchain.com/blog/building-a-harness-with-jev)

実 API に一般的な返金問い合わせを一回送り、noul・choice・score の三形式を同時に受け取れることを確認しました（実体 `typesafe/jev-1.13-20260917`）。これは接続と形式の確認であり、日本語の判定精度や継続運用時の品質を評価したものではありません。自動テストはキーの分離、入力・応答検証、設定の保存・初期化・無効化、通知の保持、フロントエンドの操作を対象とします。

タスク実行の設計参考: [Astra and JEV Minecraft agent](https://github.com/rmalde/minecraft-agent)。Hibana のタスクループは模擬 Decisions 応答と実ファイルツールで、依存順序、結果の反映、回数上限、途中停止、設定変更、利用量、作業領域の分離を検証します。通常判定 OFF・行動選択 ON の実エージェントループで、親の計画 → Jev による3操作 → 親の再計画 → Jev による2操作 → 最終回答が進むことを確認します。直接実行の拒否、設定の独立保存・初期化、途中の OFF による通常経路への復帰もテスト対象です。ブラウザー操作の振り分けは模擬ブラウザーと実画像ファイルで検証し、親への画像引き渡しもテストします。MCP の実行時無効化、Discord／エージェント送信の振り分け、送信完了状態の伝播、複数計画間のホーム接続所有権も回帰テストで確認します。実ブラウザーでのゲームプレイ、タスクループの実 API・Discord 通し実行、品質・費用の比較測定は未実施です。

並列読み取り・依存関係・失敗・キャンセルは偽の Jev 応答とツールを用いる回帰テストで検証しています。実際の応答時間の改善幅は、モデルの計画と外部サービスの待ち時間に依存します。


## Multi-Agent のトリアージ

サブエージェントが multi で「Jev 判定」が ON なら、root の最初のモデル呼び出しの前に Jev を1回だけ呼びます。
1回の Decisions 呼び出しで、次の3問を noul として同時に判定します。

- `needs_research`: 調査が必要か
- `needs_artifact_work`: 成果物の作成・変更が必要か
- `needs_review`: 独立した確認が必要か

入力は最新の依頼（4,000字まで）、画像の枚数、直前2往復の表示済みの会話だけです。システム指示・ツール出力・画像データは送りません。
結果は確率つきのヒント（`<multi_agent_triage>`）として root に渡します。確率は外れうるものとして扱い、分担は root とユーザーの指示が決めます。

判定は委譲を追加する方向にだけ使います。最初の版にあった「並列化の必要性」の質問は、低い値が root に「直接答えれば十分」と伝えて委譲を減らしたため削除しました。
調査と成果物の値がどちらも 0.5 未満なら、「1回で直接答える」ようヒントを出します。改修直後の multi は、委譲の必要がない文章作成でも子を3体起動し、Ultra（当時の Codex 由来のモード）の8倍の時間がかかったためです。
`needs_research` が 0.5 以上なら、`/root/explorer` を生の依頼で先に起動します。`needs_review` が 0.5 以上なら、納品前に実行側がレビューを行います（[納品前のレビュー](multi-agent.md#納品前のレビュー)）。
root の計画と並行して調査が進むので、調査が必要な依頼では root の最初の往復を待たずに済みます。
先行起動は通常の `spawn_agent` と同じ経路を通るため、同時実行枠・モデルと effort の方針・役割のツール制限・開始通知（「依頼に必要な情報を先に調べます。」）がそのまま適用されます。
0.5 は校正済みの精度閾値ではなく設計上の中間値です。判定が外れた場合、不要な explorer が1体動くことがあります。

期限は共有 Jev 枠の待機を含めて5秒です。当時あった完了チェックの本番実測（2026-09-23 の直近ログで 0.5〜0.8 秒）から、通常は1秒未満で終わる見込みです。
失敗・期限切れ・不正応答ではヒントを出さず、通常の multi として進めます。
Discord への通知は出さず、Jev の使用回数表示にも数えません。トークンはターンの利用量に加算します。
`Jev triage finished` には判定値・先行起動の有無・所要時間だけを記録し、依頼本文は残しません。
`/retry` や未完了作業の再開では、同じ調査を繰り返さないよう実行しません。
実 API での判定精度は未評価です。

## Anthropic の auto routing

判断記録は #35 です。プリセット「Anthropic / Auto (Jev)」（`anthropic-auto`）を選ぶと、Jev が依頼の難易度を判定し、Anthropic の API（`ANTHROPIC_API_KEY`）で使うモデルと effort を決めます。他のプリセットの動作は変わりません。

1 回の Decisions 呼び出しで 2 問を判定します。1 問目は `score` 型で、難易度の説明を易しい順に 5 つ並べます（説明にモデル名は入れません）。Jev が返す位置（端数あり）を四捨五入し、次の表の段に対応させます。2 問目は `choice` 型で、依頼がモデル（Haiku / Sonnet / Opus）を指定しているかを判定します（下の「モデルの指定」）。入力は Multi-Agent のトリアージと同じで、最新の依頼（4,000字まで）、画像の枚数、直前2往復の会話だけです。

| 段 | モデル | effort |
|---|---|---|
| 0 | Haiku 5.5 | medium |
| 1 | Haiku 5.5 | high |
| 2 | Sonnet 5.5 | medium |
| 3 | Sonnet 5.5 | high |
| 4 | Opus 5.5 | medium |

当初の表にあった Haiku 5.5 / xhigh は、本人の指示で routing の対象から外しました（#35、2026-10-08）。Sonnet 5.5 / xhigh も本人の指示で外しました（#35、2026-10-09）。本人が示した表で、Opus 5.5 / high より費用が高くスコアが低かったためです。旧段 4（量は多いが定型の作業）の説明は段 3 にまとめました。

- **モデルの指定。** 依頼の中で「Opus で答えて」のようにモデルを指定すると、難易度より指定を優先し、そのモデルに routing します。effort は、そのモデルの段のうち難易度の判定に最も近いもの（Haiku は medium / high、Sonnet は medium / high、Opus は medium）です。指定かどうかは Jev が判定し、「Opus と Sonnet の違いは？」のような言及は指定として扱いません。モデルが固定されている間は、依頼に Opus / Sonnet / Haiku（カタカナ表記を含む）の語があるときだけ Jev を呼び、指定と判定されたときだけモデルを切り替えます（切り替えると前のモデルのキャッシュは読めません）。切り替えたモデルが、その後の固定の対象になります。
- **サブエージェントは off です。** Anthropic のモデル（Auto と 3 つの固定モデル）のターンは、保存済みの設定が on / ultra / multi のどれでも、サブエージェント・Workflow・Ultra（Ultracode）なしで動きます。保存済みの設定は消さず、他のプロバイダーに切り替えると再び使われます。

- **max は使いません。** 表に max は無く、routing で決まったモデルへのリクエストは、子エージェントが effort の方針で max を指定された場合も含めて xhigh に下げて送ります。
- **保存済みの effort は使いません。** ダッシュボードや `/switch effort` の値は、このプリセットの間は無視します。
- **決まったモデルと effort は、キャッシュが消えるまで変えません。** Anthropic のプロンプトキャッシュはモデルごとに別で、bot は TTL を 1 時間に指定しています。そのチャンネルで routing 済みのモデルを最後に使ってから 1 時間以内で、会話の履歴が残っている間は、Jev を呼ばずに同じモデルと effort を使います。1 時間を過ぎたとき、履歴が無いとき（最初の発言、`/clear`、設定変更、スレッドの期限切れ、bot の再起動）は判定し直します。このため、易しい発言で始まった会話は、その後に難しい依頼が来ても 1 時間は易しい段のままです。
- **Jev が使えないときは Haiku 5.5 / high で応答します。** `JEV_API_KEY` が無い、Jev 判定（`jev_enabled`）が OFF、`TOOLS_ENABLED` / `SUBAGENT_ENABLED` が false、5 秒の期限切れ（共有 Jev 枠の待機を含む）、不正な応答のどれでも同じです。このフォールバックは固定せず、次のターンでもう一度判定します。
- スレッドの要約（compaction）は Haiku 5.5 / high で行います。他のプロバイダーの親が、子のモデルにこのプリセットを指定した場合は、子のために Jev を呼ばず Haiku 5.5 / high を使います。
- 新しく routing したターンでだけ、`Auto Routing: **Opus 5.5 Medium**` の形のメッセージを単独で送ります。新規の会話、キャッシュが消えた後（1 時間を過ぎた、履歴が消えた）の最初の発言、依頼でのモデル指定による切り替えが該当します。固定中のモデルをそのまま使うターンでは送りません。Jev が使えずフォールバックが続く間は、その会話の最初の 1 回だけ送ります。通知はツールの進捗などの途中メッセージや返信より先に届きます。Discord の表示だけで、会話の履歴には残しません。
- 判定そのものの通知は出さず、Jev の使用回数表示にも数えません。トークンはターンの利用量に加算します。`Jev route finished` には判定の結果（段・モデル・effort）と所要時間、`Auto route selected` には採用したモデルとその由来（`jev` / `requested` / `kept` / `fallback`）を記録し、依頼本文は残しません。

Anthropic の 4 つのプリセットは Premium / Moderator / Administrator だけが選べます（サーバー設定・マイ設定のどちらでも）。サーバー設定に選んだ場合は、そのサーバーのメンバー全員がプランに関係なく使えます。Claude Max など他の Premium プリセットは、従来どおり利用者ごとにプランを確認します。メンバーが使えるのはサーバーが選んだプリセットだけで、Auto を選んだサーバーでは routing 先の 3 モデルが対象になります。

検証の範囲: 2026-10-08 に実 API へ短いリクエストを送り、Haiku 5.5（medium / xhigh）、Sonnet 5.5、Opus 5.5 が同じリクエスト形で応答すること、Opus の thinking ブロックを含む履歴を Haiku / Sonnet にそのまま送れることを確認しました。routing の判定・モデルの指定・固定・期限切れ・フォールバック・サブエージェントの off は、模擬の Jev 応答を使う自動テストで確認しています。実 Jev の判定は `apps/bot/src/route-eval.ts` の依頼集で手動で確かめます（`cd apps/bot && bun run route-eval`、`JEV_API_KEY` が必要、`make ci` には含めません）。2026-10-08 の実行では、難易度の説明文をこの依頼集のうち 55 件に合わせて調整した後で 55 件すべてが期待どおりになり、調整に使っていない 30 件では 29 件が期待どおりでした（外れた 1 件は可用性と一貫性の妥協を問う設計の依頼で、Opus ではなく Sonnet xhigh になりました）。この結果は 6 段階のときのものです。2026-10-09 に 5 段階へ減らした後の実 Jev での再実行はまだで、段の数が変わるとスコアの目盛りも変わるため、上の件数はそのまま当てはまりません。調整前は、深い推論が要る依頼（証明の誤りの特定、分散システムのまれな障害の原因など）の多くが Sonnet xhigh 止まりでした。いずれも合成した依頼を前の会話なしで 1 回ずつ送った結果で、実際の Discord の依頼での精度、キャッシュのヒット率、費用は未計測です。

## 終了時の完了チェック（削除済み）

親が最終回答を返す直前に Jev で完了状態を分類し、不足があれば最大 2 回まで差し戻す「完了チェック」は、2026-10-09 に削除しました（判断記録: #50）。現在は、親モデルの最終回答をそのまま返します。`jev_enabled` は `run_jev` と multi のトリアージにだけ使います。

削除のきっかけは本番の HTTP 400 です。完了チェックが 3 回続けて不足と判定して停止すると、末尾が assistant の回答案のチェックポイントが残ります。これを `/retry` で再開すると user メッセージが足されないまま送信され、Anthropic（`claude-sonnet-5-5`）が assistant prefill として拒否しました。

400 そのものは、再開の側で直しています。`/retry` で復元した履歴の末尾が assistant なら、内部の user メッセージ（続行の指示）を足してから送信します（`resumeNote`、`apps/bot/src/checkpoint.ts`）。完了チェックが無くても、最終回答の保存後に Discord への送信が失敗すると同じ形のチェックポイントが残るためです。この経路を模擬の LLM と Discord で再現するテストがあり、修正前は末尾が assistant のリクエストになることを確かめています。実際の Anthropic API に送っての確認はしていません。
