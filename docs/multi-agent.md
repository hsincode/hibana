# Multi-Agent V2

HsinCLI fork `1b998b15ed` の `multi_agent_v2=true` を参照し、Hibana の
実行ループに V2 の協調動作を実装しています。Codex CLI 自体を子プロセスとして
起動する構成ではありません。各モデルの API には通常の effort と関数ツールを送り、
Hibana が起動・通信・待機・中断を管理します。

`ultra_mode` は Claude Code の Ultracode です。親を xhigh で呼び、
実質的な依頼ごとに Workflow ツールでワークフローを編成します
（[Ultra（Claude Code の Ultracode）](ultracode.md)）。
以前の Ultra（HsinCLI の積極的な委譲の指示文）は multi だけが使います。
on / ultra の協調ツールは、ユーザーまたは適用される指示の明示的な依頼があるときに使います。
`SUBAGENT_ENABLED=false` または `TOOLS_ENABLED=false` なら、協調ツールも Workflow も提供しません。

サーバー設定・マイ設定の「サブエージェント」は off / on / ultra / multi を選べます。
off は `subagent_enabled=false` で起動と協調ツールを無効化し、on / ultra は
`subagent_enabled=true` と `ultra_mode=false / true` を保存します。multi は
`ultra_mode=true` に加えて `multi_agent=true` を保存します（[Multi-Agent モード](#multi-agent-モード)）。
サーバー設定は具体値を保存します。マイ設定の各項目は、未設定（デフォルト）のあいだサーバー設定に従い、利用者がその項目を変えたときだけ上書きします。DM でデフォルトの項目はプロセスの初期値を使います。
`/switch ultra:on`、設定ツールの `ultra_mode`、環境変数 `ULTRA_MODE=true` で初期値を指定できます。
保存済みの effort は Ultra とは独立しています。Ultra の間は xhigh で動き、ultra を外すと保存値に戻ります。
モデルと effort は個別に変更できます。モデル変更時はそのモデルの推奨 effort を保存します。

既存の `effort: "ultra"` は読み込み時に `effort: "max"` と `ultra_mode: true` に
変換し、モデルごとの従来の effort 上限処理を維持します。旧 PATCH の ultra も
受け付けます。環境変数 `LLM_EFFORT=ultra` も、`ULTRA_MODE` が未指定・空欄なら
同じ意味です。JSONB の追加フィールドなので SQL 移行は不要です。
Jev 判定・行動選択の ON / OFF は独立しており、Ultra が設定を上書きすることはありません。
例外として multi では行動選択モードを使いません（設定値は保持し、on / ultra に戻すと再び有効になります）。

## ツールの並列実行

Chat Completions / Responses の関数ツール付きリクエストは
`parallel_tool_calls: true` を明示します。Anthropic は標準の並列ツール利用を維持します。
複数呼び出しを生成するかはモデルに依存し、実行側は検索・Web 取得・ファイル読み取り・
通常の Jev 判定を、各 Agent ループで最大6件まで同時に処理します。別名のツールも
通常のディスパッチと同じ正規化を通します。

書き込み・設定変更・シェル・ブラウザー・未知のツールは順番に実行し、前後の読み取りが
操作を追い越さないよう待ち合わせます。検索結果ごとにチェックポイントを直列に保存し、
一つの失敗で他の成功結果を失わないようにします。保存失敗や中断時にも開始済み処理を
回収してからワークスペースを解放します。

モード指示（`<multi_agent_mode>`）は HsinCLI の `multi_agent_mode_instructions.rs` と同じ2つの文面です。
multi は積極的な委譲の文面を送り、時間短縮や品質向上に役立つ並列委譲を促します（起動するかはモデルが判断します）。
on / ultra は明示的な依頼のときだけ委譲する文面です。ultra の常時の許可は Workflow ツールに対するもので、リマインダーで伝えます。
Jev の指示は別に与え、`agents__` の起動・連絡・待機・中断と Workflow を Jev の候補から除外します。
Jev と併用すると、親は独立した子やワークフローを直接起動し、自分の担当分を Jev の計画として実行できます。
子は通常のツールを使い、親が集めた結果を統合します。どのモードも Jev とは独立に設定でき、
Jev だけを ON にしても委譲やワークフローの方針は変わりません。
Jev の `parallel: true` は独立した読み取りと次の判断を重ねます。詳しくは [Jev](jev.md) を参照してください。

通常の子は開始時に `サブエージェント: GPT 6 Luna` のようなカタログ上の表示名と、
`notice` の日本語1行を残します。`message` は子への依頼全文で、チャンネルには出しません。
後続の進捗は同じ表示名を先頭に付けて共有のメッセージを編集しますが、開始通知は残ります。
追加依頼で再開したときも、その `notice` を通知します。

## Multi-Agent モード

multi は、以前の Ultra（HsinCLI の積極的な委譲）に役割チームを加えたモードです。Ultracode 化の影響は受けません。
HsinCLI の積極的な委譲の指示文をそのまま送り、root にだけ `<multi_agent_team>` の指示を追加します。
Workflow ツールは、入力にキーワード `ultracode` があるターンでだけ公開します。root はオーケストレーターとして次のように動きます。

- **委譲する依頼**: 調べる事実・複数の対象や情報源・作成や検証が必要な成果物など、独立した部分がある依頼。
  最初のツールターンで、独立した依頼をまとめて起動します。
  分け方は製品・都市・ファイル・小問など対象ごとで、観点ごとの分割はしません（範囲が重なるため）。同時実行枠（既定6）まで使えます。
- **直接答える依頼**: 挨拶・説明・短い文章作成など、手元の知識で1回で書けるもの。委譲しても遅くなるだけだからです。
- **レビュー**: 最終回答や調査結果を確認するための reviewer は、root が自分では起動しません（実行側のレビューに任せます）。
  root が reviewer を使うのは、worker の成果物を並行して確認するときと、ユーザーが自分の資料のレビューを求めたときだけです。
- **最終回答**: 子の報告を並べるのではなく、1人の専門家が書く長さに統合して納品します。表や短い箇条書きを優先し、作業経過（どの子が何をしたか・待機・中断）は書きません。

サブエージェントの有無とモードはターンの開始時に決まります。処理中に設定を変えても、その応答には適用されず、次のメッセージから反映されます。

| role | 表示 | ツール | effort（`subagent_effort` が任意のとき） |
| --- | --- | --- | --- |
| `explorer` | 調査 | 読み取りのみ（検索・Web 取得・ファイル read/list/grep・画像表示・添付取得・Discord の閲覧・スキル参照） | 継承値を medium までに抑える |
| `worker` | 作成 | 送信・公開・Discord 操作・設定変更・確認質問・認証・リモート MCP を除く通常ツール | 継承 |
| `reviewer` | 検証 | 読み取り＋シェル・ブラウザー（変更しないよう指示） | 継承 |

- `spawn_agent` に必須の `role` が加わります。on / ultra のスキーマは変わりません。
- effort の優先順位は、固定・同一の設定 → 明示の `reasoning_effort` → 役割の上限 → 継承です。
- 役割のツール制限は、ツール一覧から外すだけでなく、実行時にも拒否します。`use_tool` などの別名経由も同様です。
- Codex ハーネスはファイルをシェル経由で読むため、シェルのない explorer には read/list/grep のファイルツールを戻しています。
- 納品は root に一本化しています。子の最終回答は root への内部報告で、ユーザーには宛てません。
- 子は `send_message` / `wait_agent` / `list_agents` だけを使えます。起動・追加依頼・中断は root だけが行います。
  共有の同時実行枠を孫が奪わないようにするためです。
- 開始通知は `サブエージェント（調査）: GPT 6 Luna` のように役割名を含みます。
- Jev 行動選択モード（`run_jev_task`）は multi では公開・実行しません。操作ごとの Jev 判断が並列の子と同じ作業を直列にしてしまうためです。
- 「Jev 判定」が ON なら、ターン開始時に一度だけ Jev で分担を判定します（[Jev のトリアージ](jev.md#multi-agent-のトリアージ)）。
  調査が必要と判定したら `/root/explorer` を先に起動し、root の最初のモデル呼び出しと並行して調べ始めます。
  判定は委譲を追加する方向にだけ働き、「委譲しなくてよい」とは伝えません。
  判定に失敗しても通常どおり root が分担を決めます。`/retry` や作業の再開では実行しません。

### 役割ごとのモデルと effort

サーバー設定・マイ設定の「サブエージェント」で multi を選ぶと、役割ごとの設定表が出ます。
`multi_agent_roles` に調査・作成・検証それぞれのモデルと effort を保存し、次の3つから選べます。

| 選択肢 | モデル | effort |
| --- | --- | --- |
| 共通設定に従う（`default`、既定） | 共通の `subagent_model` を使う | 共通の `subagent_effort` を使う |
| 親と同じ（`same`） | 統括役と同じ provider / model | 統括役と同じ effort |
| 固定（`fixed`） | 指定したプリセット | 指定した effort |

- 統括役（親）は「/switch モデル」の設定を使います。たとえば親だけ Sol にするなら、メインを Sol、共通のサブエージェントを「固定: Luna」にします。検証だけ Sol にするなら、検証のモデルを「固定: Sol」にします。
- 役割の設定は、その役割について共通設定・`spawn_agent` の `model` / `reasoning_effort` 引数より優先します。explorer の effort 上限（medium）は、共通設定が「任意」で役割も「共通設定に従う」の場合だけ働きます。
- PATCH は役割・項目ごとに統合し、`null` で全役割を既定に戻します。固定プリセットには、メインや共通の固定と同じプラン・公開状態・アカウントの確認をかけます。保存済みの値に使えなくなったプリセットがあっても、その役割だけを既定に戻し、他の役割の設定は残します。
- 各役割の行には、共通設定と上書きを合わせて実際に使われるモデルと effort を表示します。エージェントが変えられる値には「（任意）」と付けます。

### 納品前のレビュー

root が最終回答を返す直前に、実行側が reviewer（`/root/final_review`）を自動で起動します。
回答案とその根拠（そのターンの依頼・子の報告・ワークスペース）を独立に確認させ、指摘を受けた root が直してから納品します。

- **起動条件**: 次のいずれかに当てはまる場合です。すでに root が reviewer を完了させていれば追加しません。
  - worker が動いた
  - Jev のトリアージでレビューの値が 0.5 以上
  - トリアージがなく、何らかの子が動いた
- **結果の扱い**:
  - reviewer の報告の1行目は `VERDICT: PASS` か `VERDICT: FAIL` にさせます。
  - PASS なら root を呼び直さず、回答案をそのまま納品します。
  - FAIL や判読できない報告なら、root に全文の書き直しを求めます。回答案はユーザーに見せていないので、修正点の列挙や補足ではなく全文を書かせます。
- **範囲**: そのターンに集めた根拠を使って確認させ、調査のやり直しや範囲の追加はさせません。
- **上限**: 1ターン1回です。120秒を超えたら reviewer を止め、回答案を納品します。ユーザーの追加入力があった場合も止めます。
- **表示とログ**: 開始通知は `サブエージェント（検証）: … / 回答案を検証します。` です。`Multi-Agent review finished` には起動理由・判定・所要時間だけを記録し、本文は残しません。

最初の本番運用（2026-09-23）では、記事の解説依頼が explorer 1体・レビューなしで終わりました。Ultra は同種の依頼で2〜3体を起動していました。
原因は次の3点でした。

- 統括役の指示が「簡単なものは自分で」「重複させない」と控えめだった。
- トリアージの低い値（並列化の必要性 0.37）が「直接答えれば十分」と伝えていた。
- レビューがモデル任せだった。

そのため、委譲を基本とする指示、追加方向だけのトリアージ、実行側のレビューに改めました。

| 委譲不要の依頼でも子を起動していた | 1回で書ける依頼は直接答える |

改善後の multi の結果です。

- **速度**:
  - 2 では、T3・T4 が改善前より大幅に短くなり（478秒→315秒、566秒→184秒）、T5 は Ultra と同程度でした。

- **読みやすさ**:
  - 改善後の比較の回答は、強みと注意点を1つの表にまとめ、Ultra の段落主体の箇条書きより読みやすくなりました。字数はほぼ同じです（815字 対 825字）。
  - 天気の回答は、出典が API の生 URL から気象庁の閲覧用ページに変わりました。
  - 作業経過の記述（「子エージェントを停止しました」など）は出なくなりました。

各条件の実行回数は1〜2回で、モデルの判断・外部サイト・レート制限による揺れを含みます。速度や品質の一般的な優劣を示すものではありません。

`/switch multi:on`、設定ツールの `multi_agent`、環境変数 `MULTI_AGENT=true` でも指定できます。
`ultra_mode=false` だけを送る古いクライアント（`/switch ultra:off` など）は multi も解除します。
`subagent_enabled=false` は常に優先されます。JSONB の追加フィールドなので SQL 移行は不要で、
保存済みの行は既定値（`MULTI_AGENT` 未指定なら false）で読み込みます。

役割の分担・先行起動とレビューの閾値（Jev の確率 0.5）・explorer の effort 上限・レビューの期限は、実測で調整した値ではなく設計上の初期値です。
自動テストで次を確認しています。

- 全カタログモデル × 4 モード × Jev 2 設定で、モード指示・役割スキーマ・`run_jev_task` の公開がそれぞれ独立していること
- 役割ごとのツールの公開と実行時の拒否
- effort の優先順位、子からの起動の拒否、root 専用指示を子へ継承しないこと
- 模擬 Jev でのトリアージ（陽性・陰性・失敗・無効・再開）
- 実際の Agent ループでの並列起動と納品の拒否

実モデルの分担判断、速度・品質の改善幅は未計測です。

## 協調ツール

API 互換性のため `agents` 名前空間は関数名の `agents__` 接頭辞で表します。

- `spawn_agent`: 非同期起動。`task_name`、`message`、`notice` が必須。`notice` は
  ひらがな・カタカナ・漢字を含む日本語1行（160文字以内）で、Discord にそのまま出します。
  即座に ID と `/root/research` のようなパスを返します。
- `send_message`: メールボックスへ追加。待機中のエージェントの新ターンは開始しません。
- `followup_task`: 履歴とモデルを保持して追加作業を開始。実行中なら追加指示を渡します。
  `notice` も必須で、再開時の表示に使います。
- `wait_agent`: メールボックスまたはユーザー入力を待機。既定30秒、最小10秒、最大1時間。
- `interrupt_agent`: 実行中のターンを中断。履歴は保持します。root と自分自身は対象外です。
- `list_agents`: 同じタスク内のエージェント、状態、直近の依頼を返します。

子から孫への委譲、兄弟・親へのメッセージ送信を利用できます。相対名は自分の
配下から解決し、兄弟や祖先には絶対パスまたは ID を使用します。最終結果は親の
メールボックスへ届き、親が統合します。処理中のツールが終わった後のメッセージ境界で
追加指示を反映し、ツール呼び出しと結果の組を壊しません。

## モデルと effort

サーバー設定は具体値を保存します。マイ設定は項目ごとにデフォルト（サーバーに従う）か、任意・同一・固定の上書きかを保存します。
サーバー側の旧 `null` は読み込み時に具体値へ変換します。マイ設定の `null` はデフォルトのままで、サーバーの値を置き換えません。
マイ設定の明示的な「任意」は、その利用者についてサーバーの「固定」を上書きできます。

| モード | モデル (`subagent_model`) | effort (`subagent_effort`) |
| --- | --- | --- |
| 任意 (`auto`、既定) | エージェントが `model` に preset ID を指定。省略時は親を継承 | `reasoning_effort` で指定。省略時は親を継承し、モデル変更時は変更先の推奨値 |
| 同一 (`same`) | 直接の親と同じ provider / model | 直接の親と同じ effort |
| 固定 (`fixed`) | ユーザー設定の `preset` を使用 | ユーザー設定の `effort` を使用 |

固定・同一の項目は `spawn_agent` の選択引数から除外し、実行時にも設定を優先します。
ワークフローの子（`agent()`）にも同じ方針を適用し、`opts.model` / `opts.effort` は「任意」のときだけ効きます。
モデルは公開状態・利用者の権限・対象アカウントの利用可否を検証します。
ChatGPT は API 側のマスターアカウント認証、それ以外は個別の API キーを確認します。
同じモデルでも Plus / Pro の認証情報を流用しません。
既存の `subagent_preset` は読み込み時にモデルの「固定」へ変換し、
新しい API 応答から旧フィールドを除去します。新規 PATCH は新フィールドを使用します。

```json
{
  "ultra_mode": true,
  "effort": "low",
  "subagent_model": { "mode": "fixed", "preset": "pro-luna" },
  "subagent_effort": { "mode": "same" }
}
```

この例では、Ultra の間は親が xhigh で動き、「同一」の子も xhigh を使います。ultra を外すと low に戻ります。

## 履歴・実行範囲

`fork_turns` は `none`、`all`、正の整数文字列を受け付け、省略・空文字は直近1ターンです。
`SUBAGENT_FORK_ALLOW_ALL` の既定は false。
`SUBAGENT_FORK_MAX_TURNS` は未指定なら数値上限なしで、指定時は `all` も禁止します。
`none` でも通常のシステム指示・ワークスペース指示は引き継ぎます。
別モデルでも履歴を継承できるよう、provider 固有の暗号化ブロックは渡さず、
実行途中のツール結果には未取得である旨を記録します。

同時実行枠はタスク全体の子・孫で共有し、既定6（root を含め7）です。
待機中のターンも枠を使用し、上限時は起動を拒否します。完了したエージェントは
枠を解放し、追加依頼時に再取得します。循環待ちを起こす起動キューは作りません。
履歴を保持するエージェントは1タスク128件、各メールボックスは128件、
通信本文は24,000文字を上限としています。

Discord の1応答タスクを1つのツリーとします。サーバー・DM・利用者をまたぐ
エージェント ID の参照は禁止し、終了・失敗・停止時は子を中断してから
ワークスペースの使用権を解放します。次の Discord 応答や `/retry` は新しいツリーで、
子のプロセス・メールボックスは復元しません。この点は CLI の永続スレッドと異なります。
ワークスペースと通常ツールは親子で共有しますが、Discord の権限チェックと
管理者の親タスク専用の自宅回線接続制限は維持します。Jev は独立した評価ツールです。

## 検証範囲

自動テストでモデル・effort の選択、旧設定移行、個人・サーバー設定の独立性、
API 権限検証、履歴継承、非同期起動、孫への委譲、メールボックス、追加依頼・中断、

カタログの全モデルについて Ultra・Jev 判定・Jev 行動選択の8通りで、設定、モード指示、

## Codex との差分点検と Jev Stop チェック（2026-09-23）

> この節は 2026-09-23 時点の記録です。Jev Stop チェックは 2026-10-09 に削除しました（判断記録: #50、[経緯](jev.md#終了時の完了チェック削除済み)）。現在は、完了を判定する仕組みはありません。

ローカルの HsinCLI `6609ae4f4b` の以下の箇所と、[Codex Hooks の Stop 仕様](https://developers.openai.com/codex/hooks) を照合しました。

- `codex-rs/core/src/context/multi_agent_mode_instructions.rs`: 2つのモード文面は一致しています（点検時は on / ultra が使用。現在は on / ultra が明示的な文面、multi が積極的な文面を使います）。
- `codex-rs/core/src/session/turn.rs`: ツール処理や追加入力がなく、モデルが終了を選んだ後に Stop hook を実行します。`decision: block` の理由は user ロールの継続入力として追加され、`stop_hook_active` が true になります。
- `codex-rs/core/src/hook_runtime.rs`: Stop と SubagentStop は別イベントです。今回の Jev 拡張は親の Stop だけを対象にします。

`fe240de` で加えた「子の報告後に必ず追加回答させる `<root_delivery>`」は Codex 由来ではないため撤去しました。以前からあった日英の送信・諦め表現に対する正規表現での書き直しも撤去し、完了判定を Jev Stop チェックに集約しています。空・途切れた API 応答の再試行は通信回復として残します。Jev の通常判定・行動選択の説明にあった追加の「子を先に起動」という指示も外し、委譲の判断は既存の multi_agent_mode に従います。

Jev Stop は `jev_enabled` に従う Hibana の任意拡張です（Multi-Agent の追加後も off / on / ultra / multi すべてで同じ判定です）。Codex 本体を変更したり、CLI の hooks.json を実行する機構ではありません。正常な最終回答はそのまま返し、明確な不足を検出した時だけ理由を追加して同じ親モデルを継続します。子の実行・待機・メールボックス・モデル選択・Ultra モードは変更しません。詳細は [Jev の完了チェック](jev.md#終了時の完了チェック削除済み) を参照してください。

この点検は委譲方針・終了判定・親子の認証経路に限定しています。Hibana は Codex CLI の完全移植ではなく、Discord ターン単位のツリー、各プロバイダーへの変換、送信権限、実行回数・Docker の上限などの適応は残ります。全 upstream 挙動との一致や実モデルの出力品質を保証するものではありません。
